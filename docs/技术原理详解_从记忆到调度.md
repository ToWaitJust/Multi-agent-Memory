## 0. 开场：一个图书馆，两类读者

先把整个系统压缩成一句话：

> **一群专家共用一座图书馆，但每个人的桌子只能摊开十本书。
> 本文讲的，就是"这十本怎么挑"。**

再展开成三句：

1. **主线 Agent** 是馆长，能看见全部馆藏（**常驻池**，490 条记忆，只读）。
2. **副线 Agent** 是被隔离在小隔间里的研究员，**只看见自己桌上那十本**（**共享池**）。
3. **调度器** 是图书管理员，负责从 490 本里挑出 ≤10 本递过去。

矛盾很直白：**桌子大小固定，馆藏无限增长**。所有工作都围绕"挑哪十本"展开。

这个课题的**创新点**不是"做个检索"，而是：

> **跨智能体的记忆共享调度** —— 挑书这件事本身，做成了一套可分维度打分、
> 权重可学习、能听反馈、还能利用话题之间依赖关系的机制。

下面从最底层往上拆。

## 1. 全景：一次提问要走七道关

```
 用户提问 "发布流程怎么走？"
         │
         ▼
┌──────────────────────────────────────────────────────────┐
│ ① 编码      query → 1024 维向量（DashScope，有落盘缓存）   │
├──────────────────────────────────────────────────────────┤
│ ② 选源      Stage A：查话题图，决定"去哪几个上游话题找"     │  ← 本课题独有
├──────────────────────────────────────────────────────────┤
│ ③ 召回      限定在这些源的记忆里，精确余弦召回候选          │
├──────────────────────────────────────────────────────────┤
│ ④ 权重      算四维权重 w（老师傅 LLM + 学徒 MLP 混合）      │
├──────────────────────────────────────────────────────────┤
│ ⑤ 打分      Stage B：每条候选算四个分，加权融合成 final     │
├──────────────────────────────────────────────────────────┤
│ ⑥ 选择      按 final 排序 + 硬约束过滤 + 配额约束 → kept    │
├──────────────────────────────────────────────────────────┤
│ ⑦ 注入      ≤10 条进共享池 → 随 prompt 送进副线            │
└──────────────────────────────────────────────────────────┘
         │
         ▼
    点赞 / 点踩 ──(虚线)──► 回到 ④，微调下次口味
```

**第 ② 步是整套系统里唯一"别的系统没有"的东西**。普通的 RAG 只有 ③~⑥：
把 query 向量丢进库里，按相似度排个序，取前 K 条。我们多了一层——**先决定去哪找，再决定找哪些**。

这就是论文主线的那句话：**多对多优于一对一**。

## 2. 第一关：记忆怎么存 —— 一个池子，N 张视图

### 2.1 双池结构

| 池 | 谁看得见 | 容量 | 落盘位置 |
|---|---|---|---|
| **常驻池**（ResidentMemoryPool） | 只有主线 | 全量（490 条） | `data/reme/<user>/main/resident_pool.jsonl` |
| **共享池**（SharedMemoryPool） | 副线 | ≤10 条 | `data/reme/<user>/sub1/shared_pool.json` |

共享池的写入逻辑很朴素——按分数插进有序表，超了就把最低分挤掉：

```python
# srtp_memory/shared_pool.py
def add(self, item):
    score = float(item.get("score", 0.0))
    if self._items and score <= self._items[-1].get("score", 0.0) \
       and len(self._items) >= self.max_size:
        return False
    self._items.append(item)
    self._items.sort(key=lambda x: float(x.get("score", 0.0)), reverse=True)
    if len(self._items) > self.max_size:
        self._items = self._items[: self.max_size]
    return item in self._items
```

**这里有个刻意的设计**：共享池**没有 `query()` 方法**。副线拿到的是全量精选集，不做二次检索。
理由：一旦副线还能自己再查，"排序/选择"这个变量就被污染了，消融没法归因。

### 2.2 一个池子，N 张视图：零拷贝的关键

上了图架构之后，需要回答一个问题：**"某个话题节点的专属记忆"在哪？**

最笨的做法是给每个节点复制一份记忆。但那样会有三个灾难：正文两份可能不一致、
每条记忆要重复算 embedding、同步成本随节点数平方增长。

实际做法是**打标记 + 建倒排**：

```python
# srtp_memory/graph/view.py —— NodeIndex
class NodeIndex:
    """owner_node → [memory_id] 倒排索引（插入 O(1)，可重建）"""
    def add(self, memory_id, owner_node):
        owner = owner_node or DEFAULT_OWNER
        prev = self._owner_of.get(memory_id)
        if prev == owner:
            return
        if prev is not None:
            self._remove_from(prev, memory_id)
        self._owner_of[memory_id] = owner
        self._by_node[owner].append(memory_id)
```

每条记忆只有**一份正文、一份 embedding**，身上挂一个 `owner_node` 标签。
"节点专属记忆"= 按标签过滤出来的**视图**，不复制任何东西。

用图书馆的话说：**书只有一本，但每本书的书脊上贴了"属于哪个专题"的标签。
换专题不用搬书，换张目录卡就行。**

### 2.3 ScopedPool：不改检索器就能限定范围

检索器的接口是 `recall(query, pool, top_k)`，只依赖 `pool.all()`。
那我塞一个"假池子"进去不就限定了范围吗——这就是 `ScopedPool`：

```python
class ScopedPool:
    """只读视图代理：把常驻池收窄到给定节点集合，接口与 ResidentMemoryPool 兼容"""
    @property
    def vector_index(self):
        return None      # ← 刻意置 None，见下
```

**为什么 `vector_index` 要返回 None？** 这是踩过的坑（缺陷 D2）：

> faiss 索引是**全池**索引。在"限定范围"下用它，它会先在全池取 top-k，
> 再和范围内的 id 求交 —— **范围内的条目会被静默丢弃**。
> 实测：范围内 4 条，只回来 2 条。

置 None 之后，`VectorRetriever` 会走 `linear_cosine_rank` 线性精确路径。
范围内也就几十条，线性算反而**更快更准，而且完全确定性**（可复现）。

### 2.4 embedding：真实向量 + 落盘缓存

三层兜底，保证任何环境都能跑：

```python
def encode(self, text):
    cached = self._cache.get(text)
    if cached is not None:
        return cached                    # ① 内存缓存，零调用
    try:
        v = self._api_encode(text)       # ② 真实 DashScope API
        if v is not None:
            self._cache[text] = v
            self._persist(text, v)       #    真实向量写盘，重启后复用
            return v
    except Exception as e:
        self._record_api_error(...)      #    失败记录 last_error，不静默
    return self._placeholder_encode(text)  # ③ 确定性哈希占位向量
```

两个关键细节：

- **真实向量落盘，占位向量不落盘**。否则你今天没 key 跑了一遍，明天补了 key，
  拿到的还是昨天的占位向量 —— 那是假的可复现。
- **API 失败要分类**：`classify_api_error()` 把错误归成 balance / auth / rate_limit / network
  等类别，中间件 `api_status()` 暴露给上层。控制台上能直接看到"余额不足"，
  而不是一个静默降级成乱码向量。

### 2.5 faiss 与线性兜底

```python
self._index = faiss.IndexFlatIP(dim)   # 精确内积 + L2 归一化 = 余弦
```

用的是 **IndexFlatIP**，**不是** IVF/HNSW 那种近似索引。原因很实在：
索引只影响召回**速度**和**候选集合**，不参与排序 —— 用精确索引能保证"换机器结果不变"。
几千条记忆用 Flat 完全够快（早期 14 节点小图上实测调度 p90 ≤ 2.4ms；
扩图后未复测该值，此处不引用具体数字）。

## 3. 第二关：候选怎么召回 —— 四个基座

`BaseRetriever` 是个抽象契约，四个中性基座实现：

| 插件名 | 做法 | 用途 |
|---|---|---|
| `retriever.full` | 全量传输，按写入序取前 K | 最原始基线 |
| `retriever.bm25` | 关键词召回（自实现 BM25，k1=1.5 b=0.75） | 传统检索对照 |
| `retriever.vector` | 1024 维余弦（faiss / 线性兜底） | **消融默认** |
| `retriever.rrf` | BM25 + 向量双路名次融合（k=60） | 融合对照 |
| `retriever.reme` | wrap ReMe 原生 search | baseline-reme 专用 |

**这里修掉过一个隐蔽缺陷**（D-9 相关）：`coordinator` 原来**从不把 `query_emb` 传给检索器**。
后果是 `retriever.vector` 退化成按 `vector_score` 排序，而那个值恒为 0 ——
于是它就变成了稳定排序，等价于 `retriever.full`。

> 也就是说，早期消融里那个"向量检索升级"**实际上根本没生效**。
> 看到指标变了，先别急着高兴——先确认你要改的东西是不是真的接上了。

修法：运行时探测签名，支持就透传。

```python
def _accepts_query_emb(retriever):
    params = inspect.signature(retriever.recall).parameters
    return "query_emb" in params
```

## 4. 第三关：选源（Stage A）—— 本课题唯一的算法增量

### 4.1 节点不是记忆条目

这是最容易讲错的一点，论文里必须写明：

> **图的节点是"一次主题会话"（topic session），不是一条记忆。**

这是它和知识图谱的根本区别。知识图谱里"节点＝实体/概念"，边是"关系"；
我们这张图里节点是**一段时间里围绕某个主题发生的对话**，边是**这些对话之间的依赖**。

一个节点长这样（`graph/models.py`）：

```python
@dataclass
class TopicNode:
    node_id: str
    topic: str = ""
    summary: str = ""
    emb: Optional[list[float]] = None   # topic(+summary) 的向量，建节点时缓存
    version: int = 1
    root_id: Optional[str] = None       # 同 root_id = 同一 topic 的不同版本
    n_memories: int = 0
```

注意 `emb` 那行的注释：**"仅用于建边与源打分，绝不进 retriever"**。
summary 也有硬边界——**只用于建边和源打分，绝不用于记忆召回**。
召回永远走实体池的原文。因为摘要会丢细节，用摘要召回等于自废武功。

### 4.2 typed 边：类型决定"默认强度"

```python
EDGE_DEFAULT_STRENGTH = {
    "derives_from": 0.9,   # 派生：A 演化出 B
    "depends_on":   0.8,   # 依赖：B 需要 A
    "references":   0.5,   # 引用：顺手提了一句
    "similar_to":   0.3,   # 相近：只是有点像
}
```

**typed 边的唯一作用就是初始化强度**，它不是分类学装饰——它直接参与配额计算。

### 4.3 边强度为什么必须是"静态"的

这是 2026-09-07 定下的案，不能改：

> `strength` 是**两个节点之间的关系属性**，建边时一次算好。
> 只在【建边 / 用户反馈 / summary 重算】三个时机变化，**绝不随 query 变化**。

代码层面有测试守护（`tests/test_graph.py::test_edge_strength_is_static`），
而且从**函数签名**上杜绝——`adjust_edge_strength(edge_id, reward)` 根本没有 query 参数。

那 query 的影响放哪？放在一个单独的动态量里：

```python
relevance = cosine(emb(topic_i), emb(query))     # 动态
src_score = λ · strength + (1 − λ) · relevance   # λ = 0.7
```

这样拆的好处：**结构是结构，提问是提问，两者可分别归因**。
而且 `emb(query)` 是 Stage B 本来就要算的那一份，复用它只有 m 次内积，
**亚毫秒、零 LLM 成本**。

### 4.4 强制 DAG：环怎么处理

图必须是有向无环图（DAG），否则"上游/下游"就没有意义了。建边前先查可达性：

```python
is_cycle = (src == dst) or self.reachable(dst, src)
if is_cycle:
    reason = "cycle_rejected"
    status = EDGE_STATUS_CYCLE_REJECTED
    type = "references"          # 降级为弱引用
    strength = 0.0
    evidence = (evidence + f" | P0环检测拒绝：{dst} 已可达 {src}，降级 references 不入邻域")
```

**不抛异常、不拒绝建边**，而是**降级成 references 且标记 `cycle_rejected`**：
这条边在溯源视图里还看得见（便于排查），但**不参与邻域召回**。

环处理的优先级是排好的：
**P0 建边环检测 > P1 扩散深度=1 > P2 路径去重 > P3 版本化（节点默认折叠）**。

### 4.5 邻域方向：为什么沿"入边"

边的语义统一为 **「被依赖方 → 依赖方」**。所以：

```python
def predecessors(self, node_id, depth=1, ...):
    """Stage A 的邻域：本节点依赖的上游源节点（沿入边展开，强边优先）"""
    return self.neighbors(node_id, depth=depth, ..., direction="in")
```

当前节点要取的"源" = 它的**入边起点**。

还有个细节：**邻域不包含自己**。

```python
# 邻域**不**包含 cur 自身 —— 自身记忆由 Stage B 直接可见，
# 若把自身当源会与"多源"语义混淆（G2 单源时就成了"只看自己"，失去对照意义）
best_edge.pop(node_id, None)
```

这行注释背后是一次真正的教训：如果把自己也算作源，那 G2（单源组）就变成了"只看自己",
"单源 vs 多源"这组关键对照**直接失效**。

### 4.6 源打分：λ 融合 + 退化保护

```python
var = _variance(rels)
if var < thr:                    # thr = 0.02
    lam, degraded = 1.0, True    # 区分度不足 → 退回纯静态
```

**为什么要这个退化保护？** 如果所有源跟 query 的相关度都差不多（方差极低），
那 `relevance` 这一项就纯粹是噪声——它会让源排序随机抖动。
这时候把 λ 拉到 1.0，退回"只看静态边强度"，反而更稳。

### 4.7 四种配额模式

| 模式 | 硬配额 | 软偏置 | 用在哪 |
|---|---|---|---|
| `none` | 无 | 无 | G0/G1（邻域全量，不做源偏向） |
| `uniform` | 每源平分 | 有 | G3 对照 |
| `strength` | 按边强度分配 | 有 | G4 |
| `soft_bias` | 无 | 有 | 默认 |

**硬配额的分配算法**（`_assign_hard_quota`）：先 `max(min_quota, round(K·w))`，
再按大小顺序增减，归一回 Σquota = K。

**软偏置**更简单粗暴：

```python
def bonus_map(self, sel, mu):
    return {s.node_id: mu * s.src_score for s in sel.sources}
```

就是把源分直接加到记忆的 final 上（`final += μ · src_score`，μ=0.2）。

这里有个 **D-032 的修正**值得单独说：

> 原先只有 `soft_bias` 模式才算 bonus，其他模式不算。
> 后来在 S-C（链式依赖）场景实测发现：**相关记忆字面根本不相似**（语义分天然低），
> 光靠硬配额管"带宽"救不回来 —— 它们在源内的 final 排名就靠后，压根轮不到。
> 改成**所有模式都叠加软偏置**。
>
> **硬配额管"带宽分配"，软偏置管"结构加成"，两者互补而非互斥。**

### 4.8 多因素边强度（F2）：一个完整的"假象复盘"

边强度最初只有一个来源：建边时的相似度（f_topic）。后来想加更多因子：

```python
f_topic     = (similarity + 1) / 2          # 主题相似度
f_temporal  = exp(-|Δt| / τ)                # 会话时间邻近（τ = 全图间隔中位数）
f_struct    = Jaccard(共同下游)              # 被同一批节点依赖 = 同一决策的上游基座
f_interact  = 1 - exp(-0.3 × interactions)  # ★ 行为证据：A 的记忆被 B 真用了多少次
```

**f_interact 是整个设计里我最喜欢的一个想法**，它的哲学是：

> **内容相似度会说谎，行为不会。**
> 两个话题主题上八竿子打不着，但 A 的记忆**反复被 B 的调度实际命中** ——
> 那这条边就该强。

实现落在两处：调度完把"进 kept 的记忆来自哪个源"记一笔（`_bump_interactions`），
重算边强度时把它算进去。

**第一版公式是这么写的：**

```python
strength = clamp01(bias + Σ wᵢ·fᵢ)
```

跑出来，"启用行为证据"的效果是 **+44%**，极其漂亮。

**但它是假的。**

检查值域之后发现：f_topic 实测落在 0.8~0.95，加上 bias 再归一化，
**所有边的强度都趋近 1.0**。后果是——

- derives_from（0.9）和 similar_to（0.3）变得一样强；
- 边强度零方差 → 强度配额**退化成均匀配额**；
- 指标"变好"的真正原因是"配额不再瞎倾斜"，跟行为证据**毫无关系**。

**修正后的公式**（D-037）：

```python
strength = clamp01( (1−α)·typed基线 + α·(Σwᵢfᵢ / Σwᵢ) )    # α = 0.5
```

**typed 默认强度作为基线保留**，多因素只在它上面做**调制**。
改完之后再测：α 在 0.3/0.7/1.0 全范围扫，f_interact 都**低于**"仅 topic 调制"的基线。

**结论：机制保留，默认不启用**（`edge_strength_weights: {topic: 1.0}`）。
它需要**真实的多轮交互数据**才有意义——合成数据里"行为"是造出来的，不是长出来的。

这个故事的价值不在于"行为证据失败了"，而在于：

> **指标变好的时候，先验证因果链是否成立，再庆祝。**
> 否则你会把一个"废掉了先验"的 bug 当成"改进有效"，写进论文，然后在答辩上被问死。

## 5. 第四关：四维打分（Stage B）

### 5.1 四个公式

每条候选记忆要拿四个 0~1 的分：

| 维度 | 公式 | 一句话解释 |
|---|---|---|
| **time** | `exp(−0.01 × Δt_hours)` | 有多新 |
| **semantic** | `0.5·cos + 0.3·vector + 0.2·bm25` | 像不像提问 |
| **frequency** | `1 − exp(−0.1 × access_count)` | 被翻过几次 |
| **task** | 匹配 1.0 / 不匹配 0.3 / 双方空 0.5 | 对不对口 |

融合：`final = Σ(wᵢ × sᵢ) / Σwᵢ`。关掉的维权重记 0，其余重新归一化（保持 Σ=1）。

语义头内部还有一层小融合（`W_COS, W_VEC, W_BM25 = 0.5, 0.3, 0.2`）——
注意这**跟 α/β 是两回事**：α/β 管"权重从哪来"，这三个系数管"语义分怎么算"。

### 5.2 三类系统性退化，和一个批级打分器

直接按上面加权融合，在真实数据上会出现三类退化（`attention.py` 里写得很清楚）：

1. **无效维浪费权重**：`frequency = 1−exp(−0.1·n)`，首轮调度时 `access_count ≡ 0`
   → 该维恒为 0，却占着 0.15 的权重。
2. **常数维退化为偏置**：同一 task_tag 下 `task` 恒为 1.0 → 对**排序**零贡献，却占 0.25。
3. **量纲不可比**：`time` 反映的是**绝对年龄**（跨模块能差 0.43~1.0），
   跟"该不该被召回"没关系；而 `semantic` 受余弦上下界约束，动态范围小。
   **等权混合会让非相关性信号稀释语义排序。**

后果实测：`G4 − G1 = −1.92%` —— 做了四维融合，反而比不做更差。

**修复**（`NormalizedAttentionScorer`，四步全在**批内**完成）：

```
A. 逐维算批内标准差，std < eps 的维判"无区分度" → 权重置 0（门控）
B. 存活维按原权重比例再分配回收的权重
C. 语义维设保底权重 semantic_floor（默认 0.5）—— 候选筛选里语义是主导信号
D. 存活维做批内 min-max 归一化，消除量纲差异后再融合
```

**这个类是"新增"的，不是"改"的** —— `attention.full` 原样保留作对照。
这样"修复有没有效"本身就可以消融（`G4` 用 full vs `G4_norm` 用 normalized）。

还有个细节：`_std()` 在 n<2 时返回 0，也就是"样本太少无法判断区分度 → 门控掉"。
宁可少用一个维度，也不让噪声维度进来搅局。

## 6. 第五关：权重谁说了算 —— 老师傅 + 学徒

### 6.1 α/β：锁死，不学

```python
hybrid = {d: self.alpha * prior[d] + self.beta * learnable[d] for d in prior}
return self._normalize(hybrid)      # α=0.6, β=0.4
```

**为什么 α/β 固定不可学？**

> 一旦让它可学，模型会偷偷把先验吞掉（比如学到 α=0.05），
> 最后你根本说不清"到底是大模型的功劳还是网络的功劳"。

**归因干净比指标好看重要。** 这是这个课题一以贯之的取舍。

LLM 先验怎么来？一个极短的提示词 + 宽容解析：

```python
LLM_PRIOR_PROMPT = (
    "为当前用户查询分配四维注意力权重（time/semantic/frequency/task），"
    "JSON 输出，和为 1，格式: {\"time\":0.2,...}"
)
# 正则抠出第一个 {...}，解析失败/网络异常 → 回退 DEFAULT_WEIGHTS
```

**失败就回退默认权重**，绝不让 LLM 抽风导致整条链路崩掉。

### 6.2 双分支 MLP：条件化切片（E3）

条件向量（E3 的"个性化"）不是给每个用户训练一个模型，
而是**把条件拼进输入**，一份 MLP 服务所有用户：

```python
class _ConditionedMLP:
    def __init__(self, query_dim=1024, condition_dim=32,
                 conditioning_dims=("semantic", "task")):
        self._global_idx = [0, 2]      # time, frequency
        self._cond_idx   = [1, 3]      # semantic, task
        self._net_global = nn.Sequential(     # 只吃 query
            nn.Linear(query_dim, 32), nn.ReLU(), nn.Linear(32, 2))
        self._net_cond = nn.Sequential(       # 吃 query + condition
            nn.Linear(query_dim + condition_dim, 64), nn.ReLU(), nn.Linear(64, 2))

    def _logits4(self, x):
        xq = x[:, :self.query_dim]
        out = torch.empty(x.shape[0], 4, dtype=x.dtype)
        out[:, self._global_idx] = self._net_global(xq)   # 全局支
        out[:, self._cond_idx]   = self._net_cond(x)      # 条件化支
        return out
```

**这里修掉过一个真实的 bug（D-047）**：原实现是**单一网络**吃 `query + condition` 拼接，输出四维。
后果是 time/frequency 的 logits **结构性受 condition 影响** ——
说好的"时间与频率全局共享"，根本没做到，是切片泄漏。

改双分支之后，验证脚本断言全局支 logits 严格不变：**Δ = 0.00e+00**。

> **验证时踩的另一个坑**：断言不能写在 softmax 概率层。
> 四维共享分母，概率之间有数学耦合，改一个维度其他三个也会动。
> 必须写在 **logits 层**。

### 6.3 条件向量怎么造

三轴（user / scenario / business）各自哈希成定长向量再拼起来：

```python
self._dims = [emb_dim // 2, emb_dim // 4, emb_dim - emb_dim//2 - emb_dim//4]  # 16/8/8
```

**为什么用哈希而不是学出来的 embedding？**

- 冷启动友好：新用户进来立刻有向量，不用等训练；
- 确定性：同一个 user_id 永远得到同一个向量，可复现；
- 空轴贡献零向量 → 未指定条件时**自然退化为全局行为**。

### 6.4 反馈闭环（E4）：一个"恒等变换"事故

反馈入口（系统级）：

```python
def submit_feedback(self, query_emb, like, condition):
    reward = 1.0 if like else -1.0
    return self.weights.update_with_feedback(query_emb, reward, condition)
```

**原实现是这样的：**

```python
target = {d: cur[d] * (1.0 + 0.1 * reward) for d in ALL_DIMS}   # 四维同乘
target = self._normalize(target)                                 # 再归一化
```

看出问题了吗？**四维同乘一个系数，然后归一化 —— 缩放被归一化完全抵消。**

```
target ≡ cur  →  loss 恒为 0  →  反馈完全无效
```

也就是说，如果没写验证脚本，这套"反馈闭环"会**带着一个永远不生效的 bug** 一路走到演示和答辩，
而且表面上看起来完全正常（loss 是 0 啊，多完美）。

**修复**：只调制条件化维。

```python
cur = self.mlp.forward(query_emb, c_emb)
target = dict(cur)
for d in self.conditioning_dims:          # 只有 semantic / task
    target[d] = cur[d] * (1.0 + 0.1 * reward)
target = self._normalize(target)
```

修完之后：正反馈 **+0.147**，负反馈 **−0.029**，20 次交替更新**有界**（不发散）。

**已知限制（V1.1）**：MLP 是共享的，对条件 A 的反馈会通过共享参数轻微影响条件 B。
真正的切片区隔需要真实多轮数据，列为后续。

## 7. 第六关：动作选择 —— 四种选择器，和一个哲学

| 插件名 | 做法 | 用在哪 |
|---|---|---|
| `selector.full` | 阈值自适应 `max(threshold, mean − 0.5·std)` | 早期默认 |
| `selector.topk` | 固定 top_k | **消融统一用**（固定 K，保归因） |
| `selector.cascade` | 语义主排序 + **硬约束过滤** | G4_qs_w（当前最优） |
| `selector.quota` | 全局排序 + **每源配额作带宽约束** | G4_qs_w |
| `selector.recency` | 按时间降序 | 附加基线 |

### 7.1 阈值 0.6 的陷阱

`selector.full` 的默认阈值是 0.6，听起来合理。**但在四维几何下它不可达**：

> 首次调度时 frequency 恒为 0（access_count=0），time 随年龄衰减，semantic 受余弦上限制约
> → 实测 final 落在 0.43~0.59 → **阈值 0.6 会把全部候选判为丢弃（kept=0）**。

所以图组的 YAML 里统一写 `threshold: 0.0`，交给自适应规则，不设魔法数字。

### 7.2 核心哲学：多维约束用"过滤"，不用"打分"

这是 `CascadeSelector` 的设计动机，也是整个项目最重要的一条方法论：

> "这个版本过时了""这个口径不对"—— 这些是**确定性判断**，
> 比连续打分**可靠且可解释**。

实测证据：归一化版的加权融合 MRR 0.783 < 原版 0.834。
**任何加权融合，当 time/task 携带的是与相关性无关的信号时，都是稀释。**

所以级联选择器分两级：

```
① 硬约束过滤（各自可开关、可独立消融）
   - task_filter    口径隔离：task 分 < 0.5（即异口径的 0.3）→ 出局
   - version_filter 版本消歧：与某条更新的记忆余弦 ≥ 0.9 → 视为旧版本 → 出局
② 语义主排序：剩下的按 final 降序取 top_k
```

还带工程兜底：**过滤后不足 top_k 就放宽**，从被过滤项里按 final 补足。
注释里写得很坦白——"这是工程兜底，不是算法妥协"。不能让硬规则把注入量饿死。

### 7.3 配额约束选择器：D-031 的教训

```python
class QuotaConstrainedSelector:
    """全局按 final 排序 + 每源配额作为带宽约束"""
```

**为什么这么设计？** 原实现把配额用在**候选阶段**（每源取前 quota 条，Σquota=K）：

> 那等于**把"选择"提前做掉了** —— Stage B 的四维排序完全没有作用空间。
> 实测后果：S-C 场景里字面不相似但确实相关的记忆，在源内排不进前 quota 就被淘汰，
> 候选命中率从"应有的全量"掉到 0.19。

正确语义：**配额只约束 kept（每源最多贡献 quota 条），候选保持全量**。
这样排序质量和带宽分配**各自发挥作用，互不掩盖**。

## 8. 第七关：成本 / 速度三角

### 8.1 三档 perf_tier

| 档 | LLM 先验 | 候选集 | λ | 标签 |
|---|---|---|---|---|
| `full` | 调 | 50 | 0.7 | 效果优先 |
| `balanced` | 走缓存 | 30 | 0.7 | 默认均衡 |
| `fast` | 关 | 20 | 1.0 | 速度优先 |

**默认档是 `fast`**，因为实测：LLM 先验花 **~1.5 秒**，只换来 **1.42pt** 的效果提升，
而且 p90 干到 1.1~1.6s，**超出 NFR-1（<1s）**。性价比极低，不值。

### 8.2 五重门控：钱要花在刀刃上

```python
def should_call_llm_prior(self, n_candidates, cache_key, source_degraded=False):
    if self.spec["llm_prior"] == "off":        return False, None, "tier_off"
    cached = self.cache.get(cache_key)
    if cached is not None:                     return False, cached, "cache_hit"
    if self.llm_calls >= self.llm_calls_per_schedule:  return False, None, "budget"
    if n_candidates <= self.min_candidates_for_prior:   return False, None, "few_cand"
    if source_degraded and self.spec["llm_prior"] == "cache":
                                               return False, None, "low_src_var"
    return True, None, "call"
```

门控顺序是**先便宜后昂贵**：缓存命中零成本，额度用完不调，候选太少不调
（4 条候选里调一次 LLM 定权重，影响微乎其微），源都不可区分时不调。

缓存 key = 归一化 query + condition 的 SHA1，LRU 512 条。

### 8.3 一个必须写下来的诚实边界

> ⚠️ **诚实边界**：本模块的升降档阈值、门槛常量是**工程启发式**，不是有客观依据的最优值。

### 10.2 评估设计（这里翻过车）

2026-09-28，涂总提了一句：

> "**正确的模式需要在正确的评估下面，在正确的场景里面才能取得好的成绩。**"

自查之后确认**三个评估错误**：

1. **K 与 |relevant| 错配**：K=5~10，但 S-A/S-B 的 |relevant| 只有 **1 条**
   → recall 只有 {0, 1} 两档，**毫无分辨力**；
2. **主指标选错**：用 recall。但四维注意力本质是**排序器**，应该用 MRR/nDCG；
3. **干扰项不够硬** → **"选错没代价"**，这才是此前所有"差异不显著"的真因。

修正后：**|relevant| 补到 3、K 收紧到 3（≈|relevant|）、主指标改 MRR+nDCG**。
梯度立刻出来了（见 §12）。

还有一条：**必须报告天花板** `ceiling = min(1, K/|relevant|)`。
ground truth 太松会制造"10/|relevant| 召回"的假象，不报天花板就会误读。

## 13. 诚实边界：没做到的和做不到的

这几条必须摊开说，不能含糊：

1. **②d 强度配额端到端价值未证**。
   G3≡G4 的数学原因很清楚：`min_quota=1` 且 K≤源数时，"每源 1 席"已用光名额，
   **没有倾斜空间**。扩图后（平均上游 2.09）仍受限于**边强度本身的质量**，
   而边强度质量最终要靠**真实多轮数据**——合成数据造不出来。
   论文里只能写"适用边界"，不能写"已证"。

2. **E3/E4 端到端无差异（D-048）**。
   条件化 vs 固定权重：0.5100/0.7900 vs 0.5233/0.7967（固定还略高，噪声级）。
   归因：**条件化和反馈的价值是随使用积累的累积效应，单轮合成评估原理上测不出来**。
   这是第三次"评估与模式假设不匹配"。解法是**多轮会话评估器**
   （同一 middleware 按序回放 + 状态跨查询延续 + 中途注入真实反馈），列为下一步首要。

3. **S-C 链式依赖仍是短板**：即使当前最优的 G4_qs_w 也只有 **MRR 0.39（K=3）/ 0.46（K=6）**，
   远低于其他场景。"加权融合稀释语义序"的机制问题还在。

4. **f_interact 行为证据机制保留但默认不启用**，等真实多轮数据。

5. **本地 15 个提交尚未推送**（GitHub 网络持续 502/SSL）。

## 14. 方法论：六条踩出来的规矩

1. **指标不动时，先怀疑实验设置，再怀疑算法。**
   三次验证：D-036 公式值域 / D-040 源池污染 / D-043 评估设置。
2. **"指标变好"先验证因果链是否成立，再庆祝。**
   D-036 靠检查"所有边强度趋近 1.0"识破了 +44% 的假象。
3. **评估必须"约束真实 + 指标对口"**：K ≈ |relevant|；排序器用 MRR/nDCG；必须报天花板。
4. **注入/改进不能污染实验变量**；消融各组统一检索器与固定 K。
5. **多维硬约束用"过滤"，不用"打分"** —— 加权融合会稀释语义序。
6. **设计要留退路**：图 `enabled=false` 时全链路行为与改造前一致；
   共享样式表不用通用类名；API 失败分类型上报而不是静默降级。

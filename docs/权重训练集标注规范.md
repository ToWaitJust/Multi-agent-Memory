# 可学习权重训练集 · 标注规范（外包交付物定义）

> 适用对象：负责产出训练样本的外包方（以下简称"标注方"）。
> 用途：训练**条件化可学习权重 MLP**（输入 `query_emb(1024) + condition_emb(32)` → 四维混合权重）。
> 本规范定义的样本，将被**直接作为蒸馏目标（reference prior）** 喂给 MLP——即"第二种喂法"：外包标签等价于权威先验，MLP 学习复现它，推理时它主导最终权重（见 §7）。

---

## 1. 一句话结论

标注方只需做一件事：**为每条用户查询，给出它应该侧重哪几个注意力维度的权重分配**。

- 不碰模型、不碰代码、不碰 embedding。
- 只产出纯文本标注文件（JSONL）。
- 每条样本 = 1 条 query + 它所处的场景条件 + 4 个维度的归一化权重。

---

## 2. 文件格式（JSONL，每行一个 JSON 对象）

```json
{
  "query": "之前那版调度器的双池同步延迟是怎么处理的？",
  "condition": {
    "user_id": "u_tu",
    "scenario_id": "research",
    "business_id": "srtp"
  },
  "target_weights": {
    "time": 0.20,
    "semantic": 0.45,
    "frequency": 0.15,
    "task": 0.20
  }
}
```

### 字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 用户真实查询文本（中文）。**必须来自真实/拟真的多智能体记忆调度场景**，不要编造与课题无关的句子。 |
| `condition.user_id` | string | 否 | 用户标识。空字符串/`null` 表示"不区分用户"。本课题默认填 `u_tu`。 |
| `condition.scenario_id` | string | 否 | 场景标识。建议取值见 §5。 |
| `condition.business_id` | string | 否 | 业务标识。本课题固定填 `srtp`。 |
| `target_weights.time` | float | 是 | 时间维度权重 ∈ [0,1]。 |
| `target_weights.semantic` | float | 是 | 语义维度权重 ∈ [0,1]。 |
| `target_weights.frequency` | float | 是 | 频率维度权重 ∈ [0,1]。 |
| `target_weights.task` | float | 是 | 任务维度权重 ∈ [0,1]。 |

### 强约束
- 四维权重**必须 ≥ 0**。
- 四维权重**之和必须 = 1**（可保留 2~4 位小数，系统会再归一化兜底，但请尽量标规范）。
- `query` 不得为空；`target_weights` 四维**缺一不可**。

---

## 3. 四维语义定义（标注方必须理解）

| 维度 | 含义 | 高权重信号（该维度应调高） | 低权重信号 |
|---|---|---|---|
| `time` 时间 | 记忆的**时效/新鲜度**，指数衰减（越新越高） | 问"最新/最近/刚/当前进展/今天/这版"；检索目标明显偏向新记忆 | 问"原理/定义/历史背景/当初为什么"等不依赖时效的内容 |
| `semantic` 语义 | 记忆与 query 的**语义相关性**（向量余弦 + BM25） | 绝大多数"是什么/怎么理解/相关概念/召回哪条记忆"类问题；这是默认主维度 | 几乎不会整体压低；仅当问题本质与内容无关（纯操作/随机）时降低 |
| `frequency` 频率 | 记忆被**访问的频繁程度** | 问"常用/反复出现的/标准流程/你经常提到的" | 一次性/偶发/临时问题 |
| `task` 任务 | 记忆与当前 **task_tag 的标签匹配**（如"写论文"/"调代码"） | query 明确带任务指向（"帮我写论文时…""调 API 那段…"），且候选记忆有 task_tag | 通用闲聊/无明确任务标签的泛问 |

> 直觉：**`semantic` 是默认底座**，多数查询它在 0.35~0.5；其余三维按"这条查询特别在意什么"往上加，并从 semantic 或其他维抠回来，保证和=1。

---

## 4. 标注示例（正反各一）

✅ 正确（语义为主 + 时间略升，因问"最新"）：
```json
{"query":"我们最新一版消融实验跑了哪 5 组？","condition":{"user_id":"u_tu","scenario_id":"research","business_id":"srtp"},
 "target_weights":{"time":0.35,"semantic":0.40,"frequency":0.10,"task":0.15}}
```

✅ 正确（任务强相关，task 拉高）：
```json
{"query":"写论文 Related Work 时，我之前整理的 ReMe 对比要点有哪些？","condition":{"user_id":"u_tu","scenario_id":"writing","business_id":"srtp"},
 "target_weights":{"time":0.15,"semantic":0.35,"frequency":0.10,"task":0.40}}
```

❌ 错误（未归一化，和≠1）：
```json
{"query":"...","condition":{...},"target_weights":{"time":0.3,"semantic":0.3,"frequency":0.3,"task":0.3}}
```
（虽然和=1 但本例是随便均分，属于"无信息标注"，应杜绝——标注必须体现 query 特性。）

❌ 错误（出现负数或缺失维度）：
```json
{"query":"...","condition":{...},"target_weights":{"time":0.2,"semantic":0.5,"frequency":0.3}}
```
（缺 `task`，不合法。）

## 5. 覆盖要求（"多场景多任务全层次"）

标注方需**主动构造**覆盖以下组合的 query，不能只堆一种：

### scenario_id 建议取值
- `research`：课题调研、读论文、方案对比
- `writing`：写论文/报告/文档
- `coding`：调代码、debug、接口对接
- `meeting`：开会、复盘、答辩准备
- `daily`：日常闲聊/通用问答

### 任务层次（task 维度从高到低的梯度都要有）
1. 强任务指向（task 0.35~0.45）：明确"写论文时/调代码时/开会时…"
2. 中任务指向（task 0.20~0.30）：隐含任务但主要靠语义
3. 无任务指向（task 0.10~0.15）：泛问，semantic 主导

### 时间层次
- 强时效（time 0.30~0.45）：最新/最近/这版
- 中时效（time 0.15~0.25）
- 弱时效（time 0.05~0.15）：原理/历史

### 频率层次
- 高频（frequency 0.25~0.35）：常用/标准流程
- 低频（frequency 0.05~0.15）：一次性

> **最低量建议**：每类组合 ≥ 10 条，全集合 ≥ 200 条。MLP 极小（1056→64→4），量大不是重点，**多样性与标签一致性**才是重点。

---

## 6. 一致性要求（多人/AI 生成务必遵守）

- 若用 AI 批量生成：请在生成 prompt 里**固化本规范的 rubric（§3）与示例（§4）**，并要求输出严格 JSON、四维和=1。生成后**人工抽检 ≥ 10%**，确认不是"全 0.25 均分"这类无信息标注。
- 标注方内部对"某类 query 该给什么权重"应有**统一判断标准**，避免同一句话被标成 {0.4,0.3,0.1,0.2} 又一会被标成 {0.2,0.5,0.1,0.2}。
- 禁止"偷懒均分"：任何样本的四维**不得出现四个值两两相等且和为 1 却无理由**的情况（除非该 query 确实无侧重，但这类应极少）。

## 7. 交付与验收

### 交付物
1. `weights_train.jsonl`：符合 §2 格式的全部样本（UTF-8，无 BOM）。
2. （可选）`weights_train.rubric.md`：标注方自己的标注细则补充说明。

> 格式参考样例见仓库 `examples/weights_train.example.jsonl`（多场景多任务覆盖，仅供对齐格式，非训练集本身）。

### 验收标准
- 每行可被 JSON 解析；`target_weights` 四维齐全、`≥0`、和∈[0.99,1.01]。
- `query` 非空且属课题相关场景。
- scenario/user/business 组合覆盖 §5 要求。
- 抽检无"无信息均分"。

### 系统如何使用（供标注方理解，无需操作）
- 训练脚本把 `query` 用**与推理相同的 DashScope embedding** 编码为 1024 维向量，与 `condition` 哈希编码的 32 维向量拼接，作为 MLP 输入。
- `target_weights` 作为蒸馏目标，batched MSE 训练 MLP。
- 由于采用"第二种喂法"，这些标签**同时作为 reference prior**：推理时若 query 命中训练集，先验直接取该标签；未命中则由已训练的 MLP 泛化给出，并被 α 地板（LLM/默认先验）约束防崩。

---

## 8. 常见疑问

**Q：要不要把记忆文本也标进去？**
A：不用。训练样本是"每条 query 一个"，标签是这条 query 的权重分配，与具体哪些记忆进共享池无关。记忆打分是 MLP 训练好之后推理阶段的事。

**Q：query 和推理时的真实 query 对不上怎么办？**
A：尽量拟真即可。MLP 学的是"query 语义 → 权重"的映射，覆盖越广泛化越好。命中不了训练集的 query 会由 MLP 泛化 + α 地板兜底。

**Q：可以只给 query 不标权重吗？**
A：不可以。第二种喂法依赖你提供的权重作为权威先验；若不提供权重，系统只能退回 LLM 先验采样（即第一种喂法），与本次约定不符。

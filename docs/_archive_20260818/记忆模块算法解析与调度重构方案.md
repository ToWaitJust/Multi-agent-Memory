## 1. AgentScope 2.0 记忆架构总览

### 1.1 重大架构变化：从 MemoryBase 到 Middleware

**重要提示**：我们安装的 AgentScope 是 **2.0.6**，其记忆架构与早期 1.x 版本完全不同。之前研究文档（《AgentScope基座系统落地方案》）中基于 `agentscope.memory.MemoryBase` 的写法已过时，需要按本文档的 2.0 架构重新设计。

| 维度 | 1.x 时代（旧） | 2.0 时代（当前） |
|------|--------------|-----------------|
| 记忆核心类 | `agentscope.memory.MemoryBase` / `ReMeModule` | `MiddlewareBase` 子类（中间件） |
| 集成方式 | Agent 的 `memory` 参数挂载 | Agent 的 `middlewares=[...]` 列表挂载 |
| 记忆管理 | 手动 `add()` / `get_memory()` | Hook 驱动：`on_reply` / `on_reasoning` / `on_system_prompt` |
| 内置方案 | `InMemoryMemory`（纯内存） | ReMe（文件+混合检索）/ Agentic（纯文件）/ Mem0（向量库） |
| 记忆注入 | 记忆列表直接拼接上下文 | 以 `HintBlock` 形式注入，或注入系统提示 |

### 1.2 2.0 记忆架构的核心概念

```
Agent（智能体）
  └── middlewares=[...]（中间件列表，按序执行）
        ├── ReMeMiddleware             → 文件化记忆 + 混合检索（本课题主选）
        ├── AgenticMemoryMiddleware    → 纯 Markdown 文件记忆
        └── Mem0Middleware             → 向量数据库记忆（mem0）

Middleware 的 Hook 契约（2.0 核心机制）：
  ├── on_reply(...)        回复前/后：截获输入、启动异步任务、写入记忆
  ├── on_reasoning(...)    推理步前：注入检索到的记忆（HintBlock）
  └── on_system_prompt(...)系统提示组装时：追加记忆指令与索引快照
```

### 1.3 关键 Hook 说明

| Hook | 触发时机 | 典型用途 |
|------|----------|----------|
| `on_reply` | 每次 Agent 回复开始/结束时 | 提取用户查询、启动异步检索任务、把本轮对话增量写入记忆 |
| `on_reasoning` | 每次模型推理调用前 | 轮询异步检索任务，完成后把记忆以 `HintBlock` 注入上下文 |
| `on_system_prompt` | 系统提示组装时 | 在系统提示中追加记忆使用说明（如 `memory_search` 工具提示、`MEMORY.md` 索引） |

**这对我们的意义**：2.0 把"记忆读写"完全中间件化。我们的记忆调度算法不再需要修改 Agent 本身，而是通过**编写自定义 Middleware**（或包装 ReMeMiddleware）来插入调度逻辑——这正好符合"继承而非修改"的扩展原则。

## 2. ReMe 记忆模块原理详解

### 2.1 ReMe 是什么

ReMe（`reme-ai`）是 AgentScope 生态的 **local-first 文件化记忆层**，核心理念是 **"Memory as File"**：把对话与资料沉淀为**带 frontmatter 和 wikilink 的 Markdown 记忆节点**，并持续完成索引、链接和整理，让后续 Agent 能够可靠召回。

其论文《Remember Me, Refine Me: A Dynamic Procedural Memory Framework for Experience-Driven Agent Evolution》已被 **Findings of ACL 2026** 接收。

### 2.2 ReMe 的三个核心能力（Job）

| Job | 功能 | 产出 |
|-----|------|------|
| `auto_memory` | 从对话轨迹中抽取有用事实（LLM 蒸馏），保留原始对话 | `session/dialog/*.jsonl` + `daily/<date>/<session>.md` |
| `auto_resource` | 把资料（网页/文档）加工为记忆节点 | daily 卡片 |
| `auto_dream` | 记忆自进化（夜间整理、建立关联） | digest 节点 |
| `search` | 渐进式混合检索 | 召回片段 + 链接展开 |

### 2.3 记忆存储结构（Memory as File）

```
workspace_dir（ReMe 工作区）
├── daily/                    # 每日工作记忆 + session 记忆卡片（auto_memory 产出）
│   └── <date>/
│       └── <session>.md      # 带 frontmatter 的记忆节点
├── digest/                   # 长期沉淀节点（auto_dream 产出）
├── resource/                 # 原始资料（auto_resource 处理）
├── session/dialog/*.jsonl    # 原始对话轨迹
├── metadata/                 # 索引元数据（可恢复）
└── MEMORY.md                 # 长期记忆索引（个人/任务/工具）
```

### 2.4 检索算法：渐进式混合搜索（核心！）

ReMe 的 `search` 是**渐进式三层展开**的混合检索，这是理解"当前记忆算法"的关键：

```
搜索流程（search_step）：
  query + limit
    │
    ▼
  候选召回：candidates = min(200, limit × candidate_multiplier[默认5])
    │
    ├──► 向量搜索（embedding，默认关闭）
    │       └─ file_store.vector_search(query)
    │
    └──► 关键词搜索（BM25 倒排索引，默认开启）
            └─ file_store.keyword_search(query)
    │
    ▼
  RRF 融合（仅当两路都有结果时）：
    fused_score = vector_weight/(60+vector_rank)
                + keyword_weight/(60+keyword_rank)
    默认 vector_weight=0.7, keyword_weight=0.3
    │
    ▼
  min_score 过滤 → 截断到 limit
    │
    ▼
  链接展开（expand_links）：
    对命中文件展开 outlinks / inlinks（默认各 10 个）
    │
    ▼
  返回：response.answer（文本）+ response.metadata（结构化）
```

**关键点**：
- **RRF 融合**：不是直接比较 BM25 分数和 cosine 分数，而是比较两个列表里的**名次**（rank），本质是排名融合。
- **渐进式**：第一层只返回最相关的 `limit` 个片段 → 第二层定位到文件（path + 行号）→ 第三层沿 wikilink 图展开邻居。搜索结果"短而可追溯"。
- **默认状态**：embedding 默认关闭（BM25 关键词检索为主），打开 `embedding_store` 后向量召回权重 0.7 更高。

### 2.5 索引构建机制

后台 `index_update_loop` 持续维护索引：
1. `init_changes_step`：启动时对比磁盘文件 mtime 与索引内 `FileNode.st_mtime`，计算新增/修改/删除
2. `watch_changes_step`：运行期间用 `watchfiles` 监听目录变化（含 quiet window 聚合）
3. `update_index_step`：Markdown 解析 → FileNode + FileChunk[] → 更新 BM25 倒排索引 / embedding / wikilink 图
4. `optimize_index_cron`：每天凌晨 2 点压缩墓碑（lazy delete 留下的）并重建索引

## 3. ReMeMiddleware 运作机制

ReMeMiddleware 是 AgentScope 2.0.6 把 ReMe 嵌入进程的官方适配层。我们已通读其完整源码，运作机制如下：

### 3.1 三种检索模式

| 模式 | 自动检索 | 工具 | 适用场景 |
|------|----------|------|----------|
| `static_control` | ✅ 回复开始时异步检索并注入 | ❌ | 无需智能体自主决策，统一注入 |
| `agent_control` | ❌ | ✅ `memory_search` 工具 | 智能体按需自主检索 |
| `both`（默认） | ✅ | ✅ | 两者结合 |

### 3.2 写入机制（自动，无手动 add 工具）

```
用户输入 → on_reply hook
    │
    ├─ 1. 快照当前上下文消息 id 集合（pre_ids）
    ├─ 2. 若 mode != agent_control 且有查询文本：
    │     启动异步检索任务 _search(query)  ← 与回复并行
    ├─ 3. 执行回复（yield 中间件链）
    │
    └─ finally:
        ├─ 取消/回收未完成的检索任务
        ├─ 计算本轮增量消息（当前上下文 - pre_ids，排除注入的记忆消息）
        └─ 调用 auto_memory job 写入增量消息  ← 每次回复自动写入
```

### 3.3 检索注入机制

```
on_reasoning hook（每次模型调用前）：
    └─ 检查异步检索任务是否完成
        ├─ 完成 → 取结果 → 构建记忆消息（HintBlock）
        │        → 追加到 agent.state.context
        └─ 未完成 → 跳过本轮注入（best-effort）
```

注入的记忆消息格式：

```python
AssistantMsg(
    name="memory",
    content=[HintBlock(hint="""## Relevant memories from past conversations
The following memories about the user may be relevant...
- <检索到的记忆条目>
""")]
)
```

### 3.4 会话隔离

- `session_id` 从 `agent.state.session_id` 动态读取（不在中间件上配置）
- 写入按 `session_id` 作用域隔离；检索跨整个 workspace
- 后台任务按 `session_id` 跟踪，多会话并发互不干扰

## 4. 三种记忆中间件对比

| 维度 | ReMeMiddleware | AgenticMemoryMiddleware | Mem0Middleware |
|------|---------------|------------------------|----------------|
| 存储介质 | Markdown 文件 + BM25/向量索引 | 纯 Markdown 文件 | 向量数据库（mem0） |
| 写入方式 | 自动（auto_memory LLM 蒸馏） | LLM 自主写文件（Write 工具） | `add_memory` 工具 |
| 检索方式 | 混合检索（BM25 + embedding + RRF + 链接） | LLM 从 MEMORY.md 索引选文件 | 向量检索 |
| 记忆类型 | daily/digest/resource + 个人/任务/工具 | user/feedback/project/reference | 用户/智能体维度 |
| 注入方式 | HintBlock | HintBlock + 系统提示 MEMORY.md 快照 | HintBlock |
| 配置复杂度 | 中（需 reme-ai 包） | 低（零依赖） | 中（需 mem0 包/服务） |
| **与课题契合度** | **⭐⭐⭐⭐⭐** | ⭐⭐ | ⭐⭐⭐ |

**结论**：ReMe 是唯一支持"对话轨迹级记忆提取 + 混合检索 + 文件可编辑"的方案，与我们的"双池记忆"研究最契合——**建议以 ReMe 为完整上下文记忆池的底层，在其上叠加我们的调度算法**。

## 5. 当前记忆模块的作用与能力边界

### 5.1 ReMe/AgentScope 记忆模块解决的问题

1. **上下文窗口限制**：早期信息在长对话中被截断/丢失 → ReMe 自动压缩会话、持久化重要信息
2. **会话无状态**：新会话无法继承历史 → 跨会话自动召回
3. **记忆不可见**：传统向量库黑盒 → "Memory as File" 让用户和 Agent 都能直接读写
4. **检索单一**：纯向量或纯关键词 → 渐进式混合检索 + 链接扩展

### 5.2 能力边界（与课题目标的差距）

这是本文档最重要的部分——**当前记忆模块"能做什么"与"不能做什么"**：

| # | 当前能力 | 能力边界/不足 | 与课题的关系 |
|---|----------|--------------|-------------|
| 1 | **单池存储**：所有记忆混在一个 workspace | 没有读写分离、没有主副线隔离 | 课题要"双池架构"：完整上下文池（全量）+ 共享池（精选） |
| 2 | **固定权重融合**：RRF 中 vector_weight=0.7 写死 | 权重不随场景变化 | 课题要"LLM 先验 + 可学习权重的混合权重模型"动态调权 |
| 3 | **两维打分**：仅语义(BM25/向量) | **无时间衰减、无频率、无任务标签** | 课题要"四维注意力"：时间/语义/频率/任务 |
| 4 | **固定 top_k + min_score**：`limit` 是固定参数 | 没有动态"保留/丢弃"决策 | 课题要"动作选择机制"按得分动态决策 |
| 5 | **检索目标是"回忆"**：找回相关片段 | 没有"调度"概念：记忆何时传给哪个智能体 | 课题要"记忆调度协调器"：主副线间记忆流转 |
| 6 | **记忆条目无注意力权重**：chunk 只有 score | 无法解释"为什么召回这条" | 课题要可解释的四维得分分解 |
| 7 | **单一智能体视角**：session 级隔离 | 无跨智能体共享记忆 | 课题要"多智能体记忆共享调度" |

### 5.3 一句话总结

> **ReMe 解决了"单个智能体如何记住并回忆"的问题；我们的课题要解决"多个智能体如何共享、筛选、调度记忆"的问题。ReMe 是完美的底层记忆基础设施，调度逻辑则完全是我们的创新空间。**

## 6. 我们的调度算法如何应用：差距分析

### 6.1 映射：课题创新点 → ReMe 现有机制

| 课题创新点 | ReMe 现有对应机制 | 应用/增强方式 |
|-----------|------------------|--------------|
| 四维注意力（时间/语义/频率/任务） | `search_step` 的 BM25+embedding 召回与 RRF 融合 | 在召回之后、返回之前，插入我们的四维注意力打分器对候选重排 |
| LLM 先验权重 | 固定的 `vector_weight=0.7` | 用 LLM 多次采样输出四维权重，替代固定值 |
| 可学习权重 | 无 | 轻量级模型（特征 → 权重），用反馈在线更新 |
| 动作选择机制 | 固定 `limit` + `min_score` | 用最终得分 + 动态阈值决定保留/丢弃 |
| 双池架构 | 单一 workspace | 完整池 = ReMe workspace；共享池 = 调度器选出的子集 |
| 书签定位 | 文件行号定位（path:start-end） | 复用 ReMe 的行号定位能力，实现"书签 = 位置快照" |
| 主副线隔离 | `session_id` 作用域隔离 | 主线/副线各自独立 workspace 或独立 session |

### 6.2 四维注意力如何融入 ReMe 检索链路

```
ReMe search 原链路：
query → [BM25召回] + [向量召回] → RRF融合 → min_score → limit截断 → 链接展开 → 返回

融入我们的四维注意力后：
query → [BM25召回] + [向量召回] → RRF融合（语义初筛，候选集可放宽到200）
      → 【四维注意力打分】          ← 我们插入的调度层
          ├─ 时间注意力：time_score（记忆时间戳 → 指数衰减）
          ├─ 语义注意力：semantic_score（query与记忆的余弦相似度）
          ├─ 频率注意力：frequency_score（记忆访问次数 → 频率编码）
          └─ 任务注意力：task_score（记忆任务标签与当前任务匹配度）
      → 【混合权重融合】              ← LLM先验 α + 可学习权重 β
          final_score = Σ w_i × attention_i
      → 【动作选择】                 ← 替代固定 top_k/min_score
          final_score ≥ 阈值 → 保留（进共享池）
          final_score < 阈值 → 丢弃
      → 保留条目进入共享记忆池 → 注入副线 Agent 上下文
```

### 6.3 双池架构如何在 ReMe 上实现

```
┌────────────────────────── 记忆层（基于 ReMe 改造）──────────────────────────┐
│                                                                            │
│  【完整上下文记忆池】= ReMe workspace（MainAgent 专属）                      │
│    ├─ auto_memory 自动写入主线对话（原始轨迹 + 蒸馏记忆卡片）               │
│    ├─ BM25 + embedding + wikilink 全量索引                                 │
│    └─ 语义初筛入口：get_candidates(query, top_k=50)                        │
│                                                                            │
│  【共享记忆池】= 调度器输出（SubAgent 专属）                                │
│    ├─ 由 MemoryCoordinator 从完整池调度选出                                │
│    ├─ 数量少、精选（10 条以内）                                            │
│    ├─ 轻量向量索引（或直接按分数排序）                                     │
│    └─ 由副线 Agent 的中间件注入上下文                                       │
│                                                                            │
│  数据流：MainAgent对话 → 完整池 → [MemoryCoordinator调度] → 共享池 → SubAgent│
└────────────────────────────────────────────────────────────────────────────┘
```

## 7. 重构方案设计

### 7.1 方案选择：两条路径

| 维度 | 方案 A：渐进式增强（推荐） | 方案 B：深度重构 |
|------|--------------------------|-----------------|
| 思路 | **保留 ReMe 作为完整池底层**，编写新的调度中间件包裹/编排它 | 完全自研双池记忆中间件，不依赖 ReMe |
| 优点 | 复用 auto_memory 提取、混合检索、文件化能力；开发量小；风险低 | 完全可控；与论文"创新点"对齐最直接 |
| 缺点 | 受 ReMe 内部实现约束（需适配其 Job 接口） | 基础建设工作量大；记忆提取质量需自行调优 |
| 适合阶段 | 阶段二（记忆层扩展，2026.08-10） | 阶段三（协调层，2026.10）深度定制时 |
| 论文叙事 | "基于 ReMe 基座的调度增强" | "自研双池记忆架构" |

**建议**：**阶段二先用方案 A 快速跑通**（把注意力/权重/动作选择作为 ReMe 检索后置的调度层），**阶段三根据实验结果决定是否演进到方案 B**。两条路径的接口设计可以保持一致，方便切换。

### 7.2 方案 A 架构设计（推荐）

```
┌─────────────────────────────────────────────────────────────────┐
│  自定义中间件 MemorySchedulingMiddleware（继承 MiddlewareBase）  │
│                                                                 │
│  on_reply:                                                      │
│    ├─ 委托内部 ReMeMiddleware 完成写入（auto_memory）           │
│    └─ 启动调度任务（查询 → 四维注意力打分 → 动作选择）          │
│                                                                 │
│  on_reasoning:                                                  │
│    └─ 注入调度结果（保留的记忆 → HintBlock）                    │
│                                                                 │
│  持有：                                                         │
│    ├─ ReMeMiddleware（完整池底层）                              │
│    ├─ MultiHeadAttentionMemoryScorer（四维注意力）              │
│    ├─ HybridWeightCalculator（LLM先验 + 可学习权重）            │
│    └─ ActionSelector（保留/丢弃决策）                           │
└─────────────────────────────────────────────────────────────────┘
```

### 7.3 方案 A 代码骨架

```python
# memory_scheduling/middleware.py
from agentscope.middleware import MiddlewareBase
from agentscope.message import Msg, HintBlock, AssistantMsg

class MemorySchedulingMiddleware(MiddlewareBase):
    """记忆调度中间件：在 ReMe 完整池之上叠加四维注意力调度"""

    def __init__(
        self,
        reme_middleware,               # 包装的 ReMeMiddleware（完整池）
        embed_model,                   # 向量化模型
        llm_client,                    # LLM（用于先验权重）
        threshold: float = 0.6,        # 动作选择阈值
        max_shared: int = 10,          # 共享池上限
    ):
        self._reme = reme_middleware   # 复用 ReMe 的写入与候选召回
        self.scorer = MultiHeadAttentionMemoryScorer()
        self.weights = HybridWeightCalculator(llm_client, embed_model)
        self.selector = ActionSelector(threshold, max_shared)

    async def on_reply(self, agent, input_kwargs, next_handler):
        # 1. 委托 ReMe 写入（auto_memory）与异步候选召回
        # 2. 在候选召回完成后，插入调度管线：
        #    候选 → 四维注意力打分 → 混合权重融合 → 动作选择
        # 3. 选出的记忆写入共享池（供副线 Agent 检索）
        async for item in next_handler(**input_kwargs):
            yield item

    async def on_reasoning(self, agent, input_kwargs, next_handler):
        # 将调度结果注入当前 Agent 上下文（HintBlock）
        async for event in next_handler(**input_kwargs):
            yield event
```

### 7.4 四维注意力打分器（适配 ReMe 候选）

```python
# memory_scheduling/attention.py
import math
import numpy as np


class MultiHeadAttentionMemoryScorer:
    """四维注意力记忆打分器（作用于 ReMe search 候选）"""

    def __init__(self, weights: dict | None = None):
        # 默认权重（后续由 HybridWeightCalculator 动态覆盖）
        self.weights = weights or {
            "time": 0.25, "semantic": 0.35,
            "frequency": 0.15, "task": 0.25,
        }

    def score(self, query_emb, memory, current_time, task_context):
        """对 ReMe 召回的一条候选记忆计算四维得分"""
        # 1. 时间注意力：记忆时间戳 → 指数衰减
        t = (current_time - memory.timestamp) / 3600.0
        time_score = math.exp(-0.01 * t)

        # 2. 语义注意力：query 与记忆的余弦相似度
        semantic_score = float(np.dot(query_emb, memory.embedding))

        # 3. 频率注意力：访问次数 → 频率编码
        frequency_score = 1 - math.exp(-0.1 * memory.access_count)

        # 4. 任务注意力：记忆任务标签匹配当前任务
        task_score = (
            1.0 if memory.task_tag == task_context.task_type else 0.3
        )

        # 5. 加权融合
        final = (
            self.weights["time"] * time_score
            + self.weights["semantic"] * semantic_score
            + self.weights["frequency"] * frequency_score
            + self.weights["task"] * task_score
        )
        return {
            "final": final, "time": time_score,
            "semantic": semantic_score,
            "frequency": frequency_score, "task": task_score,
        }
```

> **注**：ReMe 的候选 chunk 本身带 `score`（RRF 融合分），我们可以在打分时把 `score` 作为语义注意力的先验（`semantic_score = α·cosine + β·rrf_score`），实现与 ReMe 检索的平滑衔接。

### 7.6 动作选择器

```python
# memory_scheduling/selector.py
class ActionSelector:
    """动作选择：根据最终得分动态决定保留/丢弃"""

    def __init__(self, threshold=0.6, max_shared=10):
        self.threshold = threshold
        self.max_shared = max_shared

    def select(self, scored_memories):
        kept = [m for m in scored_memories
                if m["score"]["final"] >= self.threshold]
        kept.sort(key=lambda m: m["score"]["final"], reverse=True)
        return {
            "kept": kept[:self.max_shared],     # 进入共享池
            "discarded": [m for m in scored_memories
                          if m["score"]["final"] < self.threshold],
        }
```

1. 主线对话 → 主线 workspace（完整池）auto_memory 写入
2. 副线发起查询 → 调度中间件从**主线 workspace** 召回候选
3. 四维注意力打分 → 动作选择 → 生成共享池
4. 共享池注入副线上下文 → 副线回答

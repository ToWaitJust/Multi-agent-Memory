## 0. 三件事的共同根子（先说透）

三件事其实是**同一个问题的三个面**：

> **图架构落地了，但"图带来的信息"还没有被任何一环真正用起来。**

| 环节 | 现状 | 图的信息用上了吗 |
|---|---|---|
| 可视化 | 画布仍是"主副线回合时间轴"视角 | ❌ 14 节点 / 21 条 typed 边 / 边强度，一个都没画出来 |
| 效果 | 五组消融 G0 恒最高，G4 只比 G1 高 2.38% | ❌ relevant 标注只看"语义命中"，图上选源准不准对结果**无影响** |
| 边强度 | 建边时把连续相似度**压缩成 4 个离散档**（0.9/0.8/0.5/0.3），单因素 | ❌ 只用了主题相似度，时间/结构/行为证据全没用 |

所以本方案的三个部分是**一套组合拳**，且有严格的先后依赖：

```
②效果优化（改造评估场景） ← 必须先做
   ↓ 场景改造后，③边强度/打分机制的科学化才有可检验的土壤
   ↓ 场景+算法落地后，①可视化才有真数据可画（否则画的是空图）
```

**建议执行顺序：② → ③ → ①**。但①的 P0 静态视图不依赖新数据，可以并行先做。

# 第一部分 · 可视化方案

## 1.1 现状盘点

| 文件 | 现状 | 缺什么 |
|---|---|---|
| `canvas.html` | 会话画布：一回合一节点、主线绿/副线蓝、泳道、拖拽、点击进控制台、虚线=记忆继承 | **没有图拓扑视角**：typed 边、边强度、DAG 分层、Stage A 选源关系全部缺失 |
| `dashboard.html` | 节点控制台：左侧节点上下文历史、右侧调度流水线明细、双池视图（PCA 投影） | 图节点的详情（topic/summary/边列表/强度）无处展示；`/api/status` 未暴露图状态 |

**关键判断**：现有"回合时间轴"视图**不需要推翻**——它回答的是"对话怎么演进"；
图架构需要的是另一个正交视角——"**会话之间怎么关联**"。两个视图并存、互相跳转。

## 1.2 视觉方案（图拓扑视图）

### 布局：DAG 分层布局（自左向右），不用力导向

理由：图是**强制 DAG** 且边语义是"被依赖方 → 依赖方"，天然分层；
力导向布局对 DAG 的方向性表达差，且 14 节点规模力导向会抖动。
分层规则：`层号 = 最长上游路径长度`（拓扑序逐层推），同层节点按创建时间从上到下排。

```
层0        层1         层2          层3         层4
n_config → n_embed ─→ n_retrieval ─→ n_attention ─→ n_weights ─→ n_feedback
              │                          │
              └→ n_pool ────────┐        └→ n_ablation → n_dataset
                                 ↓                          ↓
                              n_graph ──→ n_demo ──→ n_deploy
                                 ↓
                              n_paper ←（n_dataset/n_metrics/n_deploy 汇入）
n_metrics（孤立上游）─┘
```
（示意：层号由最长上游路径决定；分叉/汇合一目了然——这正是"多对多"的视觉证据）

### 视觉编码（每个通道都有明确语义，不堆装饰）

| 元素 | 编码 | 说明 |
|---|---|---|
| **节点形状** | 圆角矩形卡片 | 卡片内两行：模块名（主）+ 记忆条数徽标（次） |
| **节点大小** | 随 `n_memories` 线性缩放（3 档：小/中/大） | 一眼看出哪个会话产出最多 |
| **节点底色** | 中性灰白；**当前会话节点 = 主题色描边 + 微光晕** | 与现有画布的"当前节点"语言一致 |
| **节点状态角标** | 🟢 active / ⚪ archived | 图节点有 status 字段 |
| **边颜色（四类 typed）** | `depends_on` 蓝 / `derives_from` 绿 / `references` 橙 / `similar_to` 灰 | 与图例一致，颜色沿用画布现有 CSS 变量体系 |
| **边线型** | 实线 = active；**虚线 = cycle_rejected**（P0 环检测降级边） | 把"强制 DAG"这个设计决策**可视化出来**——现在它完全不可见 |
| **边宽度** | `1px + 5px × strength`（连续） | **这是相对现状的最大改进**：强度从 4 个离散档变成连续视觉量 |
| **边方向** | 箭头（被依赖方 → 依赖方），从左指向右 | 分层布局下箭头天然向右 |
| **hover 边** | 浮层显示 `type / strength / evidence 摘要 / similarity` | evidence 字段存了建边依据，现在完全没暴露 |

### Stage A 选源可视化（图架构的核心卖点，必须最醒目）

选中任一节点时：
1. 它的**上游源节点**高亮（描边变色），非源节点降透明度至 0.35；
2. 参与选源的边**加粗 + 流动虚线动画**（CSS `stroke-dashoffset` 动画，零依赖）；
3. 每条源边上浮出 **`src_score` 标签**（λ·strength + (1−λ)·rel 的合成值，保留一位小数）；
4. 右侧详情面板列出：每个源的 strength / relevance / src_score / quota（或软偏置值）。

> 这一步做完，"**先选源再选记忆的多对多筛选**"就从论文里的一句话变成了用户能看见的东西——
> 这是答辩演示时最有说服力的画面。

### Stage B 记忆流动动画（P2）

调度发生时，从各源节点飞出若干粒子（数量=该源配额/贡献的 kept 条数），汇聚到当前节点。
粒子颜色跟随源边颜色。动画时长 600ms，不阻塞交互。
**价值**：把"多对多"从静态连线升级为**可感知的流动**；答辩演示的"哇"点。

### 控制台联动（P1）

- 点击图节点 → 右侧详情面板：topic / summary（前 8 条拼接）/ 记忆条数 / 入边列表（含强度条形图）/ 出边列表；
- 「进入会话」按钮 → 跳现有节点控制台（复用现有跳转）；
- 控制台的 `/api/status` 增加 `graph` 字段（代码里 `graph_status()` 已经写好了，只是没接出来）。

### 技术选型与工作量

| 项 | 选择 | 理由 |
|---|---|---|
| 渲染 | **继续手写 SVG**（现 canvas.html 就是手写 SVG，零依赖） | 服务器离线部署、无 CDN；14 节点规模 SVG 完全够用；不引入 ECharts/D3 |
| 布局 | 自算分层拓扑（~40 行 JS） | 算法简单（Kahn 分层），不需图布局库 |
| 后端 | `app_dashboard.py` 加 `/api/graph`（读 `data/graph/<user>/nodes.jsonl + edges.jsonl`） | `graph.persist()` 已经落盘，只差接口 |
| 动画 | CSS `stroke-dashoffset` + `transition` | 零依赖 |

### 分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| **P0** | `/api/graph` 接口 + 分层布局 + 节点/边全量视觉编码 + hover 详情 | 打开页面能看清 14 节点 21 边的 DAG；hover 任一边能看到 type/strength/evidence |
| **P1** | Stage A 选源高亮 + src_score 标签 + 右侧节点详情面板 + 控制台联动 | 点 n_graph 能看到它的 2 个上游源高亮、边上浮 src_score、右栏列出配额 |
| **P2** | 记忆流动动画 + 图状态仪表（节点数/边数/环拒绝数/精识别覆盖率） | 演示时能看到粒子从多源汇入当前节点 |

# 第二部分 · 效果优化方案

## 2.1 先对齐概念

涂总说的"性能优化"，从上下文看指的是**调度效果**（上次实验没有显著提升），不是运行速度。
运行速度已有明确结论（跳过 LLM 先验 → p90 从 1564ms 降到 2ms，已落地默认 `fast` 档），本方案不再重复。
下文"性能"均指**调度效果**。

## 2.2 根因分析（六条，按影响排序）

涂总判断"模拟记忆价值不高、场景化和逻辑关联性不成体系"——**这条成立，而且是主因**。
但不止这一条。基于已有实验数据，完整根因有六条：

| # | 根因 | 证据 | 影响面 |
|---|---|---|---|
| **R1** | **评估场景与调度价值错位**（涂总的判断，成立） | 35 个 episode 全是"X 是多少/是什么"的**事实型单点查询**。这类查询，检索器的语义序已经是最优排序——调度没有任何发力空间 | **最大**。场景不改，后面全部白做 |
| **R2** | **相关性判定与图结构脱节** | relevant 标注只看"语义是否命中查询"，不看"图上应该走哪条路径"。结果：Stage A 选源**准不准，对 recall 没有影响**——因为源池里语义命中的记忆本来就会进候选 | 图架构的核心卖点（选源）**被评估方式掩盖** |
| **R3** | **四维里三维无效**（S0 已诊断） | task 恒 1.0 / freq 恒 0 / time 是模块年龄噪声；干扰项与相关项余弦差仅 0.03，DashScope embedding 自己就能区分 | 有效信号只有语义 → 任何加权融合都是稀释 |
| **R4** | **干扰强度不够** | 干扰项与相关项余弦差 0.03，embedding 已能区分；真正需要 time/task 翻盘的场景要求差 <0.01 | time/task 维证明不了自己 |
| **R5** | **LLM 先验引入噪声且无增益** | qwen-plus 每次返回权重略不同、仅 1 次采样；B1 实测去掉先验只损失 1.42pt 却省 99.9% 延迟 | α 侧（先验融合）目前是负资产 |
| **R6** | **评估维度单一** | 单 user / 单 scenario / 单轮调度；无跨用户方差 → 条件化（申报书创新点②的另一半）完全没被检验 | 条件化 MLP、反馈闭环的价值无法体现 |

**一句话总结**：不是"调度做得不好"，而是"**评估场景里根本没有调度能赢的题**"。
检索器的语义序在这套事实型查询上就是最优解，我们却在用 recall@K 衡量"谁排得更像语义序"。

## 2.3 优化方案：改造评估场景，让调度有题可做

按"**先给调度出难题，再检验组件**"的思路，把数据集从单一"事实型查询"扩展为 **5 类场景**。
每类场景**精确对应一个调度组件**——这样哪个组件有用、哪个没用，一看便知：

| 场景 | 描述 | 考验的组件 | ground truth 标注逻辑 |
|---|---|---|---|
| **S-A 时序演进** | 同一事实存在多个历史版本（阈值 0.7→0.65→0.6），**只有最新版有效**；旧版语义几乎相同 | **time 维** | relevant = 仅最新版；旧版本标注"已取代" |
| **S-B 口径隔离** | 同一参数在不同任务口径下取值不同（研发 0.6 / 运维告警 12 / 教学演示 0.5）；查询带口径标签 | **task 维** | relevant = 与查询口径一致的版本；异口径标注不相关 |
| **S-C 链式依赖** | 做出 A 模块的决策，必须先知道 B 的约束、C 的前提（2~3 跳的链）；查询只提 A，**不提 B/C 的名字** | **Stage A 选源（图结构）** | relevant = 链上所有节点的关键记忆；**同时标注"应参考源路径"** |
| **S-D 偏好漂移** | 同一用户在"性能调优"和"写论文"两个场景下，对同一批记忆的偏好排序不同 | **条件化（condition）** | 两套 relevant 排序，按 scenario 分别标注 |
| **S-E 频率反馈** | 模拟多轮交互：某些记忆被反复命中（access_count > 0），应比同语义的冷记忆优先 | **freq 维 + 反馈闭环** | 需要多轮调度模拟（先调 N 轮再看第 N+1 轮） |

**S-C 是图架构的正名之战**：只有在"查询不提上游模块名字"的链式依赖里，Stage A 的选源
（沿边找上游）才能做到**语义检索做不到的事**——语义检索只会召回与查询字面相似的记忆，
而链式依赖的 B/C 节点记忆与查询**字面不相似**。这是图结构真正的、语义检索替代不了的价值。

### 配套改造

| 项 | 内容 |
|---|---|
| **评估指标升级** | 每类场景**分组报告**（不再只看总平均）：S-A 看 time 增益、S-B 看 task 增益、S-C 看选源增益、S-D 看条件化增益、S-E 看反馈增益。**哪个组件在哪个场景有用，一目了然** |
| **ground truth 扩展** | relevant 之外增加"**应参考源路径**"字段（S-C 用），指标加"路径命中率" |
| **相关性判定与图挂钩** | S-C 的 relevant 必须包含"查询字面不相似、但图上必需"的记忆——这是让 R2 逆转的关键 |
| **多用户矩阵（R6）** | 3 用户 × 3 场景，检验条件化是否真的"千人千面"（哪怕偏好差异是构造的） |

### 分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| **E1** | 实现 S-A + S-B 两类场景（改造成本最低：只需在现有记忆上加版本/口径维度） | time/task 维在对应场景组里产生**正向增益**（哪怕只有 2~3pt） |
| **E2** | 实现 S-C 链式依赖场景 + "应参考源路径"标注与路径命中率指标 | G4 在 S-C 组的 recall **显著高于 G0**（G0 无选源，只能靠语义撞） |
| **E3** | 实现 S-D 偏好漂移 + 3×3 用户矩阵 | 条件化开关在 S-D 组产生可测差异 |
| **E4** | 实现 S-E 多轮频率模拟 | freq 维从"恒 0"变成有区分度 |

**风险与诚实预期**：E1 的 time/task 增益**可能仍然很小**——因为 DashScope embedding 对
"0.7 vs 0.6"这种区分度很好（余弦差 0.03）。若如此，方案是**给干扰项做"近似复述"处理**
（同义改写而非换个数字，把余弦差压到 <0.01），这个成本可控。

# 第三部分 · 边强度与注意力打分机制的科学化方案

## 3.1 边强度：从"相似度分档"到"多因素融合"

### 现状与问题

```python
# 现状（graph/models.py）：建边时只用主题相似度，且压缩成 4 个离散档
sim >= 0.85 → derives_from (0.9)
sim >= 0.72 → depends_on  (0.8)
sim >= 0.58 → references  (0.5)
其他         → similar_to (0.3)
```
**两个问题**：
1. **单因素**：只用主题相似度。涂总提的"时间关联性"没用上；更重要的**行为证据**（跨节点实际引用）和**结构角色**（共同被依赖）也没用上。
2. **连续值压成 4 档**：sim=0.84 和 sim=0.73 都映射到 0.8 → 丢失区分度；而 0.86 和 0.99 映射到同一个 0.9 → 强度天花板被封死。

### 方案：**type 与 strength 解耦 + 多因素线性融合**

**核心原则**：`type` 表达"关系的**语义类别**"（派生/依赖/引用/相近），`strength` 表达"关系的**强弱**"（连续值）。
两者解耦后，强度不再被迫装进 4 个档位。

```
strength = σ( b + w₁·f_topic + w₂·f_temporal + w₃·f_struct + w₄·f_interact )
```
σ 为 sigmoid（映射到 0~1），各因素先归一化到 [0,1]：

| 因子 | 定义 | 归一化 | 数据来源 | 现状 |
|---|---|---|---|---|
| **f_topic** 主题相似 | `cos(emb(topicᵢ), emb(topicⱼ))`，用 summary 后的向量（比"topic+首问"更准） | (cos+1)/2 | 建边时已算 | ✅ 已有 |
| **f_temporal** 时间关联 | 会话时间窗的邻近度：`exp(-\|Δt\| / τ)`，τ = 全图会话间隔的中位数（自适应，不拍脑袋） | 指数归一 | 节点 created_at | 🆕 涂总提的方向，需定义清楚 |
| **f_struct** 结构角色 | **共同下游占比**：两节点被同一批节点依赖的比例（DAG 里比"共同邻居"更有意义——被同一批下游依赖，说明它们是同一决策的上游基座） | Jaccard | 图拓扑 | 🆕 图论做法 |
| **f_interact** 交互强度 | A 节点的记忆在 B 节点的调度中被实际命中（进 kept）的次数，做饱和归一 `1-exp(-0.3n)` | 饱和归一 | **调度埋点**（已有 kept 记录） | 🆕 **行为证据，比内容相似更硬** |
| **f_explicit** 显式依赖（可选） | 用户会话中显式说"基于 X 会话的结论"→ LLM 抽取 | 0/1 | LLM | 🆕 可选，P3 |

**权重 w₁~w₄ 的确定**：不拍脑袋，**用数据学**——
在 S-C（链式依赖）场景上，以"路径命中率"为目标做**网格搜索或逻辑回归**拟合
（把"真边 vs 假边"作为标签，各因素作为特征，拟合出的权重就是有数据依据的）。
这一步同时产出论文里需要的"权重敏感性分析"。

### 更新时机（保持"静态 + 受控更新"哲学，扩展为四时机）

| 时机 | 动作 | 对应因子 |
|---|---|---|
| 建边时 | 多因素初始融合 | f_topic / f_temporal / f_struct |
| 调度反馈后 | bandit 微调（已有 `adjust_edge_strength`）+ **累计 f_interact** | f_interact 渐进积累 |
| summary 重算 | 重算 f_topic（已有 `recompute_strength_from_summary`） | f_topic |
| 图演化后（新节点加入） | 重算受影响边的 f_struct | f_struct |

### 消融设计（证据链）

| 组 | 因子组合 | 验证什么 |
|---|---|---|
| E0 | 仅 f_topic（现状） | 基线 |
| E1 | + f_temporal | 时间关联是否有增量 |
| E2 | + f_struct | 结构角色是否有增量 |
| E3 | 全因子 | 完整方案 |
| E4 | 去掉 f_interact | 行为证据的贡献 |

**验收**：S-C 场景的"路径命中率"随因子增加而单调提升；若不提升，如实报告并简化。

### 对涂总思路的回应

涂总提的"节点主题相似性、时间关联性"**方向正确，但只覆盖了 2/4**：
- 主题相似性 = f_topic（现状已有，问题是被压成 4 档）；
- 时间关联性 = f_temporal（需要定义清楚"关联"是什么：我建议用**会话时间窗邻近度**而非简单时间差）；
- **缺的两块恰恰可能是最有用的**：f_struct（共同被依赖 = 同一决策的基座）和
  f_interact（实际被引用 = 行为证据）。**内容相似度会说谎，行为不会**——
  两个节点主题上很像，但如果 A 的记忆从没在 B 的调度里被用过，这条边就该弱。

## 3.2 注意力打分机制：从"加权融合"到"语义排序 + 硬约束过滤"

### 现状问题（S0 已诊断 + 本轮归一化扫描的新证据）

```python
# 现状：四维各自算分，加权融合
final = 0.25·time + 0.35·semantic + 0.15·frequency + 0.25·task
```
- **S0 已诊断**：task 恒 1.0、freq 恒 0、time 是模块年龄噪声 → 有效信号只有语义；
- **归一化扫描新证据**：把无区分度维门控掉、权重再分配给 time（floor=0.5），**反而更差**
  （MRR 0.783 vs full 0.834）—— 因为 time 在本数据上是噪声，**权重再分配放大了噪声**；
  `floor=1.0`（回收权重全给语义）≈ 纯语义排序，与 G0 持平。

### 结论：**问题不在"权重怎么分"，在"该不该加权"**

> **当 time/task 携带的是与相关性无关（或弱相关）的信号时，任何加权融合都是稀释；
> 它们的正确用法不是"打分"，而是"过滤"。**

### 方案：**语义主排序 + 多维硬约束过滤（级联式）**

```
第一级（语义主排序）：semantic 分排序（检索器语义序，不动）
第二级（硬约束过滤）：
   ├─ 版本过滤：同一事实链上，非最新版本的记忆 → 直接出局（time 维的正确用法）
   ├─ 口径过滤：task_tag 与查询口径不一致 → 直接出局（task 维的正确用法）
   └─ 频率惩罚：同语义组内，低频记忆排在末位（freq 维的正确用法）—— P3
第三级（软偏置）：图源软偏置 μ·src_score（已有，保留）
```

**为什么级联比加权好**：
1. 语义序的**纯度不被稀释**（不再乘 0.35 的权重）；
2. time/task 的价值以"**排除错误项**"体现——这本来就是它们最擅长的
   （"这个版本过时了"是确定性判断，比"这个记忆有多重要"的连续打分更可靠）；
3. **可解释**：用户问"为什么这条没被注入"，答案是"它是旧版本"（硬规则），而不是"四维加权后它低了 0.02"（黑盒）；
4. **实验上可精确检验**：过滤规则对就是对的，不像加权融合那样混在一起说不清。

### 各维的"科学化"改造（过滤语义下重新定义）

| 维 | 现状 | 问题 | 改造方案 |
|---|---|---|---|
| **time** | `exp(-0.01·t_h)` 绝对年龄，参与加权 | "越新越好"是**错误的归纳偏置**——真相是"同一事实只有最新版有效"，与绝对年龄无关 | **版本链消歧**：同一事实的多个版本（靠语义近邻聚类识别"这是一个事实的多个版本"）→ 只保留最新。time 从"连续打分"变成"**离散的版本选择**" |
| **task** | 字符串相等 → 1.0/0.3/0.5 | 字符串相等太粗："运维口径"和"教学口径"都≠"研发"，但它们和研发的距离显然不同 | **口径向量**：把 task_tag 从字符串改为口径描述文本的 embedding；查询时用查询里的口径词（或用户 profile）的向量算余弦 → 软匹配。过滤阈值可配 |
| **frequency** | `1-exp(-0.1·全局访问次数)` | 全局次数首轮恒 0，且"全局高频"不等于"对这个用户有用" | **条件化频次**：按 (user, scenario) 分桶计数——该记忆**在这个用户这个场景**下被命中几次。这同时接上了反馈闭环（点赞=强化的频次信号） |
| **semantic** | `0.5cos + 0.3vec + 0.2bm25` | 无大问题，是唯一有效维 | 保持；归一化扫描已证明它该拿大头 |

### 与条件化/反馈闭环的关系（申报书创新点的自洽）

级联式方案**不削弱**申报书创新点②，反而让它更清晰：
- **语义排序** = 检索器能力（不是本课题的贡献，如实承认）；
- **硬约束过滤** = time/task 维的结构化应用（**本课题贡献**：把"融合多维属性"具体化为"多维约束下的版本消歧与口径隔离"）；
- **条件化 MLP + 反馈闭环** = 个性化的动态适应（**本课题贡献**：S-D/S-E 场景检验）；
- **图选源** = 多对多的结构先验（**本课题贡献**：S-C 场景检验）。

即：从"四维加权融合"这个**难以证明**的主张，转向"**多维约束 + 结构先验 + 条件化适应**"这个**可分别证明**的主张组合。

## Q1. 图结构到底带来多少增益？（归因问题）

**为什么是问题**：加了图之后效果变好，无法区分是"图结构提供了更好的候选范围"还是"调度算法更好"。审稿人一定会问。

**怎么验证**：消融链里必须包含 **G1 = 图 + 均匀调度**（结构有、算法无）作为下界，和 **G2 = 图 + 单源调度**（等价于主副线）。
- 若 `G4 − G1` 显著 → 算法贡献为主 ✅
- 若 `G1 ≈ G4` → 图结构贡献为主，算法的创新主张被削弱 ❌

**判据**：`G4 − G1` 在 recall_acc 或 task_completion 上提升 ≥ 5%（绝对值），且 `G4 > G2` 显著。

**状态**：未开始（依赖 Q4 数据集）

## Q2. "先选源再选记忆"这一层是否真的有价值？

**为什么是问题**：这是图相对主副线唯一新增的算法含量。如果这一层没用，图就退化成可视化成本。

**怎么验证**：**G3（多源 + 四维打分，但配额均匀分配）vs G4（多源 + 四维 + 边强度配额）**，两组只差"边强度是否参与配额"。
- `G4 > G3` → 边的量化参与有效 ✅
- `G4 ≈ G3` → 边强度没用，Stage A 退化成随机选源 ❌（此时应简化，图只保留邻域限定）

**判据**：G4 在**源召回命中率**上显著高于 G3（≥8%），且不牺牲跨源相关性。

**状态**：未开始

## Q3. 节点粒度怎么定？一个 topic 到底多大？

**为什么是问题**：节点太细（每轮对话一个节点）→ 图爆炸、边无意义；节点太粗（整个项目一个节点）→ 退化成单节点，等于没做图。

**怎么验证**：
1. 取一个真实长会话，人工标注"主题边界"；
2. 用两种自动切分策略（按轮次窗口 / 按语义漂移阈值）分别切，与人工标注比 F1；
3. 观察不同粒度下**平均节点数**与**边密度**（节点数 5–30、平均度 2–4 视为健康区间）。

**判据**：存在一组自动切分参数，使平均节点数落在 5–30、平均出度落在 1.5–4 之间，且与人工标注 F1 ≥ 0.6。

**状态**：未开始

## Q4. 数据集从哪来？

**为什么是问题**：没有带真实 topic 结构的会话数据，整个 idea 无法验证——这是**当前最大的阻塞项**。

**候选方案**：

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A. 自建（推荐先试） | 用 AgentScope 跑一个"多模块项目"场景（如：写一个含 5 个子模块的小系统），每个子模块 = 一个 topic 会话，天然形成 DAG | 结构真实、可控、与现有运行时无缝 | 规模小、自证嫌疑（需人工审图结构是否合理） |
| B. 改造公开数据集 | 找多会话/长程对话数据集（如 LoCoMo、MSC），把 session 当节点 | 规模大、客观 | 需要判断 session 间关系是否天然成图；可能只是链 |
| C. 合成 | 脚本生成带 ground-truth 的 topic 图 + 记忆 | ground-truth 明确、可精确计算指标 | 人工痕迹重，说服力最弱 |

**判据**：至少拿到 ≥1 个数据集，能构造出 **≥10 个节点、≥15 条边、且含至少 1 个分叉（一个节点有两个下游）** 的图。

**状态**：未开始（**阻塞项，优先做**）

## Q6. summary 的两个坑

**Q6c.（新增）冷启动：建边时还没有 summary，怎么办？**
- 问题：主张"节点形成时做关系识别"，但节点初建时只有 topic 标题 + 首轮 query，summary 尚未生成。
- 当前方案：**两阶段建边** —— 粗识别（topic 标题 + 首轮 query embedding，建节点时立即）→ 精识别（summary 生成后，可覆盖粗识别，须写 `evidence` 溯源）。
- 判据：精识别覆盖粗识别的比例应 < 30%（否则说明粗识别太差，不如直接等到 summary 再建边，但那样节点初建期无邻域可用）。

**Q6a. summary 失效后如何重算？**
- 问题：topic 后续发展，早期 summary 过时 → 基于它建的边全错。
- 需要设计：重算触发条件（新记忆 N 条 / 相似度下降阈值）+ **重算时要能溯源到 `memory_id`**，否则不知道拿什么重算。
- 判据：给出触发规则，且重算后能列出"受影响需要重新判定的边"。

**Q6b. summary 丢细节 vs `path:line` 书签定位冲突？**
- 问题：现有书签定位依赖精确细节，summary 天生丢细节。
- 当前立场：**summary 只用于关系识别，绝不用于记忆召回**；召回一律走实体池原文。
- 判据：在代码层面强制这一边界（summary 字段不进入 `retriever` 的输入）。

**状态**：立场已定，未在代码中落地

## Q8. 边强度是否 per-query 重算？（已定：不重算，2026-09-07）

**问题**：调度时是否要为每个 query 重新测算边强度？

**结论（已定）**：**不重算。** 拆成两个量——
- `strength`：**静态**，节点间关系的属性，建边时一次性算好，仅在「建边 / 用户反馈 / summary 重算」三种时机变化；
- `relevance`：**动态**，`query × 节点` 的属性，`cos(emb(topic_i), emb(q))`。

融合 `score_source = λ·strength + (1−λ)·relevance`，**λ = 0.7 固定为架构超参，不进消融变量链**。
理由：若 strength 随 query 变，它就不再是"边"的属性，概念自相矛盾，且会导致边强度震荡、实验不可复现。

**仍需验证的子问题**：
1. **λ 取多少合理？** → 敏感性分析（λ ∈ {0.5, 0.7, 0.9, 1.0}），放进论文附录，**不单独开消融组**（避免组数膨胀）。
2. **query 项到底带来多少增益？** → 用 λ=1.0 与 λ=0.7 两组对比，报告在附录；若增益 < 2% 则承认纯静态够用（对用户提案有利）。
3. **退化保护阈值**：`relevance` 方差低于多少时退回纯静态？需实测标定。

**判据**：λ=0.7 相比 λ=1.0 在 `source_hit_rate` 上有正向增益（≥2%），且不牺牲可复现性（embedding 缓存命中）。

**状态**：设计已定，待实测标定

## Q7.（新增）手动选源 vs 自动扩散，默认哪个？

**为什么是问题**：用户明确表达"用户最好能够自己选定信息来源"，但自动扩散才是算法价值的体现。二者都要留，但默认项会影响消融的主指标口径。

**怎么验证**：在 POC 里同时跑两种模式，比较：
- 手动选源（用户/oracle 勾选正确源）→ 代表**上限**
- 自动扩散 → 代表**算法实际水平**
- 随机选源 → 代表**下界**

**判据**：自动扩散 ≥ (手动上限 − 随机下界) × 60% + 随机下界，即算法能拿到人工选择大部分的价值。

**状态**：未开始

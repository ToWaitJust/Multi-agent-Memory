# 05 · Q4 数据集方案 A：「todo-cli 多模块项目」场景设计

> 目的：给 idea 的 go/no-go 提供**带真实 topic 结构**的数据集（02 的 Q4，阻塞项）。
> 同时为主线生产在线消融语料（一份数据喂两条线）。

## 1. 场景设定

用一个"AI 团队分工开发 CLI 待办工具「todo-cli」"的多智能体项目：6 个子模块 = 6 个 topic 会话，
每个会话由一个 Agent 承担，依赖关系天然形成 DAG。

## 2. 模块与依赖 DAG

```
M1 配置模块 ──┬──▶ M3 核心逻辑 ──▶ M4 命令行解析
M2 存储模块 ──┤        └─────────▶ M5 统计报表
              ├──▶ M6 异常与日志      ▲
              └──────────────────────┘（M2→M5, M2→M6）
```

| 节点 | 模块 | 关键词域 | task_tag |
|---|---|---|---|
| M1 | 配置模块 | 配置文件加载 / 默认值 / 路径解析 | config |
| M2 | 存储模块 | JSON 持久化 / schema 字段 / 读写 | storage |
| M3 | 核心逻辑 | 增删改查 / 优先级 / 截止日期 | core |
| M4 | 命令行解析 | 子命令 / 参数 / 帮助文本 | cli |
| M5 | 统计报表 | 完成率 / 逾期统计 / 周报 | stats |
| M6 | 异常与日志 | 异常分类 / 日志格式 | exlog |

边（src → dst 语义：dst 依赖 src），type 与 strength 用 typed 默认值：

| 边 | type | strength |
|---|---|---|
| M1→M3, M2→M3 | depends_on | 0.8 |
| M3→M4, M3→M5 | depends_on | 0.8 |
| M2→M5 | depends_on | 0.8 |
| M1→M6, M2→M6 | depends_on | 0.8 |

> 注意：本 POC 用**设计图（真实依赖）作为边**，不做关系识别。关系识别的质量是 Q6，
> 单独验证——若混在一起，"图错了导致效果差"和"调度差"又分不开（归因纪律）。

## 3. 会话生成协议（每模块 2 轮，拓扑序执行）

- **Round 1**：给定项目背景 + 依赖模块的已产出记忆（模拟图调度注入），要求输出 5 条关键设计决策（每条一行）。
- **Round 2**：指定其中一条决策展开细节（字段名/接口签名），3-5 行。
- 每行输出解析为 **1 条记忆**（text 原文，node_id 记来源，task_tag = 模块名）。
- 预计每模块 8-12 条记忆，全图 50-70 条；LLM = `model.dashscope`(qwen-plus)，embedding = DashScope 1024 维（带落盘缓存）。

## 4. 查询与 ground truth（关键：防天花板假象）

6 条查询，**relevant 节点 ⊆ cur 的入边邻居**（POC 第一轮教训：标注必须与边方向一致），
每条查询给 anchor 关键词，**相关记忆 = 相关节点中含 ≥1 anchor 的记忆**，且生成后**必须检查 |relevant| ≤ K=10**
（超过就收紧 anchor，否则 recall 被 10/|relevant| 压死——第一轮发现 2）。

| 查询 | cur | relevant | anchor |
|---|---|---|---|
| RQ1 | M3 | M1,M2 | 配置 / schema |
| RQ2 | M4 | M3 | 增删改查 / 接口 |
| RQ3 | M5 | M2,M3 | 字段 / 优先级 |
| RQ4 | M5 | M2 | 读写 / 存储 |
| RQ5 | M6 | M1,M2 | 路径 / 读写 |
| RQ6 | M6 | M1 | 配置 |

生成数据集后人工抽检：打印每条查询的 relevant 记忆原文，确认标注合理（Q4 判据的人工环节）。

## 5. 评测

`run_real_poc.py` 与合成 POC 共用 `stage_a.py` 与打分器，只换两处：
- embedding：假向量 → **真实 DashScope 1024 维**（落盘缓存，可复现）；
- 数据：合成图 → 本数据集。

判据不变（G4S vs G2 vs G3），另报告 |relevant| 与 recall 天花板。

## 1. 动机：主副线的空间自由度不足

当前架构是**星形拓扑**：一条主线（MainAgent，完整上下文池，全量只读）+ N 条副线（SubAgent，隔离沙箱，注入共享池 ≤10 条）。

副线之间是**互不感知**的。这在单轮小任务里没问题，但在真实大项目场景下会撞上三个硬伤：

| 硬伤 | 表现 |
|---|---|
| **远丢失** | 副线 B 的产物本应是副线 C 的输入，但 B、C 之间没有通道，只能绕回主线，主线上下文一旦膨胀就丢 |
| **不可控** | 用户想指定"只参考第 3 个模块和第 7 个模块的结论"时，星形结构没有表达"模块"这一层的概念 |
| **死板** | 子模块产物天然是其他节点的输入 → 真实结构里存在**中间节点** → 逻辑上它就不是星，而是图 |

**结论**：主副线的"线"是一个特例（两层星），图是它的推广。从 AI Native 的角度看，记忆的组织方式应当跟着任务结构走，而不是被预设成两层。

### 1.1 与知识图谱的根本区别（论文必须写明）

> **知识图谱以"记忆条目/实体"为节点；我们以"topic 会话"为节点。**

- 节点粒度 = **一次主题会话**（一个子任务、一个模块、一轮讨论），不是一条记忆。
- 节点内部仍装着一个记忆池（引用式），节点之间靠边连接。
- 因此不存在"实体对齐/关系抽取"这类知识图谱的经典难题，代价是**无法做实体级推理**——这不是本课题的目标，需要在论文里主动划清边界。

## 2. 数据模型

### 2.1 Node（topic 会话节点）

```python
@dataclass
class TopicNode:
    node_id: str            # uuid
    topic: str              # 主题标题（用户可见）
    summary: str            # 一次性生成的摘要，用于关系识别（§7）
    owner_user: str
    session_id: str
    created_at: float
    version: int = 1        # §5 版本化，默认 1
    root_id: str = None     # 版本链根（同 root_id 视为同一 topic 的不同版本）
    status: str = "active"  # active / archived
    pool: list[NodeMemoryRef] = field(default_factory=list)   # 视图池，见 §2.3
```

### 2.2 Edge（关系边）

```python
@dataclass
class TopicEdge:
    src: str
    dst: str
    type: str        # derives_from / depends_on / references / similar_to
    strength: float  # 0~1，参与计算（§4），可被反馈调整
    created_at: float
    evidence: str    # 建边依据（谁、依据什么判断出的关系），用于溯源
```

**typed 边的唯一作用 = 默认强度初始化**（不是分类学装饰）：

| type | 默认 strength | 语义 |
|---|---|---|
| `derives_from` | 0.9 | B 是从 A 派生出来的产物（A→B 强相关） |
| `depends_on`   | 0.8 | B 依赖 A 的结论才能进行 |
| `references`   | 0.5 | B 只是参考了 A |
| `similar_to`   | 0.3 | 主题相近，弱关联 |

**强度可被反馈调整**（点赞/点踩 → 微调该边 strength），这样边就不是死的元数据，而是**可学习的带宽**。

### 2.3 NodeMemoryRef（引用式条目）

```python
@dataclass
class NodeMemoryRef:
    memory_id: str      # 指向实体池主键，正文不在节点里
    score: float        # 该条在此节点语境下的分数
    via_edge: str       # 从哪条边/哪个源节点来（溯源）
    from_node: str
```

## 3. 存储架构：1 实体池 + N 视图池

**废弃"两个扁平池"的想法**（常驻池 + 共享池各存一份记忆），原因是：新增节点时，另一池里的记忆会成为召回盲区，且两份正文会失效不一致。

改为：

```
┌───────────────────────────────────────────────┐
│  EntityPool（常驻实体池，唯一正文存储）          │
│  memory_id → {text, embedding(1024d), meta,    │
│               producer_node}                    │
│  ↑ 副线产物也写回这里，只打 producer_node 标记   │
└───────────────────────────────────────────────┘
        ▲ 引用（memory_id）        ▲ 引用
   ┌────┴─────┐              ┌────┴─────┐
   │ Node A 池 │              │ Node B 池 │   ← 视图池，只存 {memory_id, score, via_edge}
   └──────────┘              └──────────┘
```

- **正文只有一份** → 存储不爆炸、失效自动一致；
- **溯源保留** → `producer_node` 标记能回答"这条记忆是谁产出的"；
- **统一检索空间** → 新节点召回不会漏掉别的节点产出的记忆。

> 这不是"双池架构被废弃"，而是**双池从「2 个扁平池」进化为「1 实体池 + N 视图池」**。原有常驻池语义（per-user 全量）仍在，共享池语义（注入副线的 ≤10 条）演化为每次调度动态生成的视图。

## 4. 边必须参与计算（否则图白做）

这是整个 idea 的成败点。边如果只做元数据，图就只剩可视化价值，等于引入巨额架构成本换一个好看的界面。

边在调度中承担**三层作用**：

### 作用 1：邻域筛选（限定检索范围）
新节点只从**邻域子图**召回，而不是全池。这直接解决"远丢失"—— 隔着十万八千里的记忆本来就不该被召回。
- 强边（strength ≥ 阈值）优先扩展；弱边仅在强边召回不足时启用。

### 作用 2：跨源配额（边强度 = 带宽）★ 核心
边强度决定**该源节点能贡献几条记忆到最终注入集**。

```
quota(s_i) = 配额分配( normalize(strength_i for s_i in S), K )
```

比如 K=10，三个源节点边强度 0.9 / 0.5 / 0.3 → 配额大致 5 / 3 / 2（保底 1 条，避免零配额饿死）。
这一步**在记忆打分之前**，是新增的一层。

### 作用 3：路径去重
同一 `memory_id` 经多条路径到达时，**取强度最高的一条**，不重复计分、不重复占配额。

## 4.5 边强度是**静态**的：不要 per-query 重算（重要澄清）

> **结论：关系识别在节点形成时一次性完成，边强度此后是常量。调度时不重算边强度，只在边强度之上叠加一个 query 相关度项。**

### 4.5.1 两个被混淆的概念

之前"边强度参与计算"的表述容易被误解为"每次 query 重新测算边强度"——**这是错的**。必须拆成两个量：

| | `strength`（边强度） | `relevance`（查询相关度） |
|---|---|---|
| 是谁的属性 | **节点间关系**的属性 | **query × 节点**的属性 |
| 是否依赖 query | **否** | 是 |
| 何时计算 | **建边时一次性算好** | 调度时算 |
| 何时变化 | 建边 / 用户反馈 / summary 重算 | 每次 query |
| 能否人工改 | 可以（用户调边权） | 不可以 |

**如果 strength 随 query 变，它就不再是"边"的属性**，概念上自相矛盾，也不再是可解释的结构先验。

### 4.5.2 调度时用的实际量

```
score_source(s_i | q) = λ · strength(edge(n_cur → s_i))  +  (1 − λ) · cos( emb(topic_i), emb(q) )
                        └──── 静态，建边时定 ──────────┘   └── 动态，复用已有 embedding ──────┘
λ = 0.7（静态主导），固定为架构超参，不进消融变量链
```

**关键：这一项几乎零成本。**
- `emb(q)` —— Stage B 语义头**本来就要算一次 query embedding**，直接复用；
- `emb(topic_i)` —— 节点 summary / topic 的 embedding 在**建节点时就已缓存**（1024 维，DashScope + 落盘缓存）；
- 因此增量只是 m 次向量内积（m = 源节点数，通常 2–5），亚毫秒级，且**完全可复现**（embedding 有缓存）。

### 4.5.3 为什么还是要有 query 项（纯静态会失效的场景）

> 节点 n 的邻居：A = 「架构讨论」(strength 0.9)、B = 「数据集讨论」(strength 0.6)。
> 当 query = "消融实验的数据集从哪来" 时，纯静态会把更多配额给 A —— 错了。

但**在 topic 图里这个损失可控**：节点是按主题切出来的，源池主题相对纯净 —— A 池里凑不出数据集相关的记忆，多给的配额只是**浪费**而不是**污染**。
推论：**纯静态的失效程度 ∝ 源池主题混杂度**，而这正是 topic 级节点（相对"记忆条目做节点"）的优势所在。

### 4.5.4 代价阶梯（L0 / L1 / L2）

| 层级 | 做法 | 成本 | 定位 |
|---|---|---|---|
| **L0 纯静态** | 只用 `strength` 查表 | O(1)，零 LLM | 最简单、最可解释；**用户原始提案** |
| **L1 静态 × query 调制** ★推荐 | `λ·strength + (1−λ)·cos` | ≈ 0（复用 query embedding） | 默认实现 |
| L2 per-query LLM 判定 | 每次 query 让 LLM 重新判边 | 高、慢、不可复现 | **不采用** |

**L1 相对 L0 的额外成本接近零，因此没有理由退回 L0。**
退化保护：当各源 `cos` 的方差 < 阈值（区分度不足）时，自动令 λ=1 退回纯静态。

### 4.5.5 边强度的**更新时机**（穷举，仅此三种）

1. **建边时**：粗识别 + 精识别（见 §7 两阶段）；
2. **用户反馈时**：点赞/点踩 → 微调该边 `strength`（与现有 `update_with_feedback` 一致，受正则约束防漂移）；
3. **summary 失效重算时**：触发受影响边的重新判定（Q6a）。

> **不因 query 更新。** 这一条要写进代码约束，防止后期实现时偷懒把 query 信号写回边强度（会导致边强度震荡、实验不可复现）。

## 5. 两阶段调度管线（多对多筛选的具体形态）

```
                    ┌────────────── Stage A：选源 ──────────────┐
  当前节点 n_cur ──▶ 邻域展开（depth=1，强边优先）
                 ──▶ 环检测 / 版本折叠
                 ──▶ 源打分 score_source = λ·strength(静态) + (1−λ)·cos(topic_i, q)
                     （strength 建边时定，不重算；emb(q) 复用 Stage B 语义头）
                 ──▶ 配额分配 quota(s_i)          → 源集合 S = {s_1..s_m}
                    └──────────────────────────────────────────┘
                    ┌────────────── Stage B：选记忆 ────────────┐
  每个 s_i 的视图池 ─▶ 四维打分 f_d(m, query)  d∈{time,semantic,frequency,task}
                 ──▶ 混合权重 w = α·LLM_prior + β·MLP(condition)   （α=0.6, β=0.4）
                 ──▶ 源内按 score 取前 quota(s_i) 条
                 ──▶ 跨源合并 + 按 memory_id 去重（取 max）
                 ──▶ 截断 top-K（≤10）              → 注入集
                    └──────────────────────────────────────────┘
```

### 关键公式

**记忆分**（沿用现有四维设计，不改）：
```
score(m) = Σ_d  w_d · f_d(m, query)        d ∈ {time, semantic, frequency, task}
w        = α · w_prior(LLM 实时单次采样) + β · w_learned(MLP, condition 条件化)
```

**源打分与配额**（新增，见 §4.5）：
```
strength_i  = edge(n_cur → s_i).strength              # 静态常量，建边时定，不 per-query 重算
rel_i       = cos( emb(topic_i), emb(q) )             # 动态，复用 Stage B 语义头的 emb(q)
src_score_i = λ · strength_i + (1 − λ) · rel_i        # λ = 0.7 固定超参
              （若 rel 的方差 < 阈值 → λ 置 1，退回纯静态）

quota(s_i)  = max(1, round( K · softmax(src_score/τ)_i ))     τ 为温度，默认 0.5
             然后按比例归一化回 Σquota = K
```

**去重**：跨源合并时同一 `memory_id` 只保留 `score` 最高的一份，`via_edge` 记最强来源。

### 与现有实现的兼容点（重要）

- 四维打分、`α/β` 混合权重、条件化 MLP（仅语义/任务随 user/scenario 漂移）、反馈闭环 —— **全部原样保留**，图只加 Stage A。
- 检索基座（`retriever.vector` / `bm25` / `full`）继续在**实体池**上工作，Stage A 只负责缩小候选源，不改变检索原语。
- 因此工程量 ≈ 新增 `graph.py`（Node/Edge/邻接/环检测）+ `source_selector.py`（Stage A）+ 调度器里插入一次调用，**不推翻现有代码**。

## 6. 环（cycle）与版本化

### 6.1 问题
环会导致：无限迭代不收敛、路径重复计分、同一节点被反复召回。

### 6.2 处理策略（按优先级）

| 优先级 | 手段 | 说明 |
|---|---|---|
| **P0 主要** | **建边时环检测** | 加边前做可达性检查；若 `dst` 已可达 `src` → **默认拒绝建边**，提示改打 `references`（弱引用，不参与调度邻域召回，仅用于溯源） |
| **P1 扩散封顶** | **扩散深度 depth = 1**（默认） | Stage A 只展开一跳邻域，天然封住传播；depth=2 作为消融变量可选 |
| **P2 去重** | **路径去重** | 同 memory_id 多路径到达取最强一条 |
| **P3 兜底** | **版本化节点** | 仅在用户显式要求"延续该 topic 生成新版本"时才建：`A_v1 → B → A_v2`，`root_id` 相同 |

### 6.3 关于"版本化导致节点爆炸"（用户质疑，已采纳）

**版本化不作为主要手段**，原因正是节点数量与用户选择负担：

- 版本节点**默认折叠**，用户可见的源选择列表只展示**主版本**，版本链在溯源视图里才展开；
- 用户选的是**源节点（topic 级）**，不是记忆条目 —— 选择负担是 **topic 数量级（几个到几十个）**，不是记忆数量级（上千条）；
- 加上 P0 拒绝建边 + P1 深度封顶，实际会触发版本化的场景极少。

### 6.4 用户自主选定信息来源（两种模式并存）

| 模式 | 说明 | 适用 |
|---|---|---|
| **手动勾选源节点** ★默认 | 用户在 topic 列表里勾 2–3 个源节点，配额按勾选项平均或按强度分配 | 可控、论文里好讲、符合"用户最好能自己选"的诉求 |
| **自动邻域扩散 + 配额** | 系统按边强度自动展开邻域并分配配额 | 省事，体现算法价值，是消融里要证明的对象 |

两条路共用 Stage B，差异只在 Stage A 的源集合怎么来 —— 实现上就是一个 `source_mode: manual | auto` 配置位。

## 7. 关系识别：怎么做出来边

**方案（用户提出）**：一次性为每个 topic 生成 summary，此后新节点**只与已有 summary 比对**来识别关系，避免 O(n²) 全量比对。

```
新节点 ──▶ 与所有既有节点 topic 表征算相似度（embedding 余弦，O(n) 且 n 为节点数）
      ──▶ top-k 候选 ──▶ LLM 判定边类型 ──▶ 建边（默认 strength 由类型决定）
```

只保留 top-k（k=3~5）建边、其余不建 —— 这是**边密度的第二道控制阀**（第一道是 §Q3 节点粒度）。

### 7.1 冷启动问题：建边时还没有 summary（两阶段建边）

"节点形成时就做关系识别"有个时间差：**节点刚创建时只有 topic 标题和首轮 query，summary 要等积累若干记忆后才生成**。

因此识别分两拍：

| 阶段 | 时机 | 依据 | 特点 |
|---|---|---|---|
| **粗识别** | 建节点时**立即** | topic 标题 + 首轮 query 的 embedding | 快、可能不准，保证节点一诞生就有边可用 |
| **精识别** | summary 生成后 | 节点 summary 的 embedding（+ 可选 LLM 复核） | 准，**允许修正/覆盖粗识别结果** |

精识别覆盖粗识别时**必须写 `evidence` 溯源**（记录：初判依据、修正依据、时间戳），否则图的可解释性会被破坏，也无法回答"为什么这两个节点连着"。

### 7.2 已识别的待解决问题（详见 `02_open_questions.md` Q6）

1. **summary 失效**：topic 后续发展后 summary 过时，需要重算；重算时要能溯源到 `memory_id` 才知道重算依据，这个链路尚未设计。**且重算会连带触发受影响边的重新判定**（§4.5.5 更新时机之三）。
2. **细节丢失**：summary 会丢掉细节，而现有 `path:line` 书签定位依赖精确细节 —— 二者冲突，需要明确 **summary 只用于关系识别与源打分，绝不用于记忆召回**（召回走实体池原文）。此边界需在代码层强制（summary 字段不进 `retriever` 输入）。

## 8. 需要新增的指标

现有指标只有**压缩比 / token_reduction / recall_acc / latency**，不足以刻画多源场景：

| 新指标 | 定义 | 为什么需要 |
|---|---|---|
| **多源覆盖率** | 注入集中来自 ≥2 个不同源节点的条目占比 | 证明"多对多"真的发生了，而不是退化成单源 |
| **跨源相关性** | 注入集中每条记忆与其源节点 topic 的平均相关分 | 防止为了凑覆盖率拉进无关记忆 |
| **源召回命中率** | 人工标注的"应当被参考的源节点"中被实际选中的比例 | 直接衡量 Stage A 的选源质量 |
| **去重率** | 合并时被路径去重掉的重复条目数 / 合并前总数 | 衡量多路径冗余程度 |

> 这些指标缺失，`03_ablation_design.md` 里的 G3/G4 就无法证明任何东西。

## 9. 未决与已知风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 数据集来源 | 需要有真实 topic 结构的数据集才能验证（Q4） | 候选：AgentScope 多轮项目型会话自建 / 公开多会话数据集改造 |
| 图可视化工作量 | 现有 dashboard 是主副线视角，改成图视图是有量工作 | 先做 headless，可视化后置（P2） |
| 归因风险 | 图结构本身可能带来大部分提升 | 消融必须含 G1（图 + 均匀调度）作为下界（见 03） |
| summary 质量 | 关系识别全靠 summary，summary 差 → 图全错 | 需人工抽检 + 边置信度阈值 |
